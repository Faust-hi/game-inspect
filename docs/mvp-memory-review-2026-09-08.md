# Оценка MVP и разбор завышения/занижения аппаратных требований

Проверен checkout `5d93a3c`; до работы дерево Git было чистым. Это целевой разбор
расчётного ядра и проверок приложения, а не полный аудит безопасности или
доказательство соответствия всем возможным стандартам. Приложенный текст рассмотрен
как набор гипотез. Исторические результаты предыдущих аудитов не заменяли новые проверки.

## Состояние учебного MVP

Архитектура FastAPI / SQLAlchemy / SQLite / React достаточна для локального учебного
продукта. Есть разделение API, схем, репозиториев и расчётных сервисов, миграции,
транзакционная изоляция тестов и объяснения решений. Микросервисы, новый framework
или абстрактные слои ради «clean architecture» сейчас не нужны.

Основной риск — предметная модель: вычисления воспроизводимы, но абсолютная стоимость
работы и объём ресурсов заданы экспертно. Это пригодно для демонстрации поддержки
решений с оговорками; надёжный минимум оборудования ещё не установлен.

Поддерживаемость ухудшает концентрация таблиц коэффициентов, затрат кадра, памяти,
совместимости и подбора оборудования в `backend/app/services/hardware.py` (около 2000
физических строк до правки). Выделять стоит самостоятельные расчёты памяти и подбора,
сохранив единую точку сборки результата. Массовая косметическая переработка не приоритетна.

README и реестр требуют согласования с кодом: в README есть ссылки на отсутствующий
`services/feedback.py`, будущая формулировка про уже существующий Playwright и обещания
калибровки; реестр называет этап модели завершённым и калибровку пройденной, тогда как
`practice_check()` явно сообщает об отсутствии независимой проверки. Полный старый
реестр этой точечной работой не переаттестован.

## Что подтвердилось в приложенном разборе

| Тезис | Результат проверки текущего кода |
|---|---|
| Большие постоянные расходы памяти для лёгких игр | Подтверждено: ОС 2,5 ГБ, движок 2 ГБ, render targets 1,8 ГБ VRAM при 1080p, базовое аудио 0,35 ГБ RAM; затем добавляются streaming и контент. Четыре перечисленных слагаемых дают **5,0**, а не 5,25 ГБ RAM. |
| Расход движка зависит от версии/сцены | Сейчас `_memory_components` не использует engine/version. Но число «100–300 МБ для Source» из приложения не проверено замером и не годится как новая константа. |
| Нет встроенных и слабых GPU | Не подтвердилось: seed содержит Intel HD 4600/520, UHD, Vega и GT 730 2 ГБ. У многих iGPU `vram_gb=null`, загрузчик преобразует это в 0, а фильтр вместимости исключает их. Неизвестный бюджет shared memory не равен доказанной недостаточности GPU. |
| Минимальный CPU — только i3-8100 | Неточно: есть Ryzen 3 1200 с меньшим ST-индексом. При этом нижняя граница CPU-каталога действительно ограничивает выбор; год модели не является метрикой производительности. |
| `target_quality=high` зафиксирован | Да, в **скрипте внешнего прогона** `run_batches.profile_of`; в приложении качество выбирается пользователем. Смена на Ultra ради совпадения с требованиями недопустима. В текущей формуле `tex_quality(high)=1,28`, `ultra=1,56`; приведённые в приложении значения 1,0/1,2 не соответствуют коду. |
| Новым AAA обязательно нужен более новый CPU | Не доказано. Нужны целевой base FPS, конкретная сцена, критический путь CPU и сопутствующая подготовка рендера; год GPU/CPU не заменяет эти данные. |
| Мало перечисленных функций занижает всю память | Не буквально: `content` считается из масштаба, объектов и NPC, а не количества функций. Функции добавляют CPU/GPU-нагрузку и влияют на отдельные ветки памяти; «добавить галочки» — недостаточное исправление. |

Старый/новый и лёгкий/тяжёлый — разные признаки. Высокое качество разных игр
не означает одинаковую техническую сложность. Оптимизация полезна также для физики,
AI, потоковой загрузки, стабильности времени кадра и памяти. Баланс качества и скорости
— один вид компромисса; другие методы сохраняют изображение, но требуют больше памяти,
предварительной обработки или времени разработки.

## Исправленная ошибка и предел результата

Удалено принудительное `RAM >= VRAM + 4 ГБ` и добавочные общие нижние пределы после
суммирования компонентов. ОС и движок уже присутствуют в составе. RAM и VRAM теперь
суммируются независимо в общей функции, которую используют оба расчётных пути.
Экспертная доля CPU-копий пока сохранена и явно названа допущением. Версия алгоритма
повышена до `2.4.1`, чтобы отличать новые результаты от сохранённых снимков.

Основание: промежуточные CPU-ресурсы загрузки могут переиспользоваться после завершения
операций GPU; постоянной полной копии всей VRAM в RAM API не требует.
См. [Microsoft: uploading resources](https://learn.microsoft.com/en-us/windows/win32/direct3d12/uploading-resources),
[Microsoft: fence-based resource management](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management).
Следовательно, сравнение общей RAM с VRAM само по себе не определяет возможность запуска.

В ответ добавлены ограничения фиксированных расходов движка/памяти и объяснение,
почему встроенная графика с неизвестной вместимостью не проходит подбор. Численная
калибровка, заявленный RAM минимум Portal и совместимость iGPU этим **не установлены**.

| Внешний профиль (те же входы и пустая корзина) | RAM до, ГБ | RAM после, ГБ | VRAM после, ГБ |
|---|---:|---:|---:|
| Portal | 8,8 | 8,6 | 4,8 |
| Armored Core VI | 9,4 | 9,3 | 5,4 |
| Grand Theft Auto V | 21,8 | 16,3 | 17,8 |
| DOOM Eternal | 11,4 | 11,4 | 7,3 |
| Alan Wake 2 | 17,6 | 12,4 | 13,6 |

Это изменение арифметики, **не доказательство улучшения точности**. Некоторые оценки
AAA стали ниже: устранение лишнего слагаемого не восполняет недостающие реальные затраты.
Portal по-прежнему завышен относительно обсуждаемого ориентира. Нельзя компенсировать
эту проблему возвратом неверного неравенства.

Полные 58 входов, компоненты, результаты, версия и SHA256 исходников сохранены в
`validation/memory-before.json` и `validation/memory-after.json`. Они не являются
независимым эталонным набором и не загружаются приложением.

## Как решать основную проблему без усложнения MVP

Последовательность: **описание работы → исходные затраты → выбранные методы и их
компромиссы → подбор совместимого оборудования**. Сейчас описание работы недостаточно
различает технически разные игры. Одна глобальная поправка не устранит обе стороны ошибки.

1. Сначала определить сценарий оценки: версия игры/движка, сцена, ОС, разрешение,
   конкретные настройки и базовый FPS без генерации кадров. Исторические системные
   требования и современный полный расход системы хранить раздельно. Неизвестные
   настройки внешних профилей отмечать как неизвестные, а не выдавать default High за факт.
2. Добавить небольшой технический профиль сложности, отдельный от названия качества:
   резидентные текстуры (размеры/форматы/mips), видимая геометрия, сложность материалов,
   динамический свет/тени/RT, активная симуляция и поток данных. Для короткой анкеты
   допустимы объяснимые сценарии сложности с явной неопределённостью; их численные
   диапазоны должны происходить из измерений или ресурсных бюджетов.
3. Память считать по реально описанным ресурсам: текстуры и геометрия, размеры и форматы
   render targets, число одновременно живущих буферов, CPU-копии, staging/streaming,
   runtime движка и резерв ОС. Буфер `width × height × bytes_per_pixel × samples`
   имеет физический смысл; универсальные 1,8 ГБ при 1080p — гипотеза. Уменьшение числа
   пикселей не должно автоматически уменьшать всё содержимое текстур или всю RAM.
4. Для CPU использовать активные задачи и их частоты; для GPU — геометрию, шейдинг,
   проходы и RT. Затраты подготовки RT учитывать в соответствующей подсистеме, когда
   они известны, без искусственного порога «современный CPU». Epic отдельно описывает
   построение acceleration structures, память и CPU-подготовку в
   [Ray Tracing Performance Guide](https://dev.epicgames.com/documentation/unreal-engine/ray-tracing-performance-guide-in-unreal-engine).
5. Разделить выбор реализации и дополнительную оптимизацию уже выбранной реализации.
   Нельзя повторно считать готовую оптимизированную игру как неоптимизированную базу,
   а затем ещё раз начислять экономию за её штатные технологии. Профиль готовой игры
   и проектный сценарий «до внедрения корзины» должны явно различаться.
6. Shared memory описывать на уровне конфигурации CPU+iGPU+RAM: доступный общий пул,
   пропускная способность и оставшаяся память ОС/игре. Значение `0` не заменять
   произвольными 4/8 ГБ и не подбирать встроенный GPU независимо от совместимого CPU.
7. Проверять отдельно лёгкие старые, тяжёлые старые, лёгкие современные и тяжёлые
   современные сценарии, включая неграфические CPU/streaming-нагрузки. Подбор по
   названию или году не использовать. Отчёт должен показывать и переоценку, и недооценку
   CPU/GPU, память, совместимость и долю сценариев с достаточными исходными данными.

Таким образом, лёгкая современная игра тоже сможет получить небольшой бюджет, а старая
игра с тяжёлой симуляцией — заметную CPU-нагрузку. Достичь этого только текущим набором
грубых входов нельзя: разные реальные нагрузки могут превращаться в одинаковый профиль.

## Проверки этой работы

- До правки: `pytest backend/tests validation -q --tb=short` — 402 passed, 1 skipped.
- После: 405 passed, 1 skipped; 15 предупреждений устаревающих API Starlette/httpx.
  Добавлены проверки независимых RAM/VRAM, отсутствия дополнительного floor,
  совпадения двух расчётных путей и объяснения неизвестной вместимости GPU.
- Frontend: 53 unit-теста прошли; typecheck и production build прошли.
- Playwright в headless Edge на временной БД: **1 failed**. Сценарий ожидает кнопку
  «Сохранить» в header, а текущий `App.tsx` показывает только «Проект» и
  «Администрирование». Это существующее расхождение интерфейса и теста; в этой работе
  frontend не менялся. Тест не удалён и не ослаблен ради зелёного отчёта.
- Linux, нативные игровые движки и реальный FPS этим прогоном не проверялись.

Воспроизведение диагностического отчёта из корня репозитория:

```text
.venv/Scripts/python.exe validation/diagnose_memory.py validation/memory-new.json
```

Скрипт создаёт только отдельную БД в памяти и новый файл отчёта, отказывается
перезаписывать существующий файл. Исторические партии и рабочая БД не изменяются.

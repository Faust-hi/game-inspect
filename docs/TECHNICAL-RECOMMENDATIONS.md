## Рекомендации

Сквозные методы теперь остаются в своей технической функции вместо общей группы. Метод без назначенной функции сравнивается только с собой. Добавление другой функции не меняет ранг внутри исходной группы. Первый вариант сопоставимой группы из двух методов больше не теряет пометку лидера из-за деления ранга на размер группы.

Критерий соответствия ресурсам учитывает нагрузку CPU/GPU для функции в текущем профиле вместе с пользовательскими бюджетами. Поэтому изменение частоты физики, количества объектов, разрешения и других технических параметров влияет на критерии сравнения. TOPSIS остаётся относительным экспертным ранжированием, а не вероятностью успеха или процентом ускорения.

Убраны безусловные утверждения, что стадия запрещает архитектуру, обязательно требует полной переделки, гарантирует выигрыш алгоритмов или подтверждает отсутствие стриминга по отсутствию одного конкретного метода. Дополнения и перекрытия больше не называются доказанным усилением.

## Работа с реализованной корзиной

1. Выберите функции и решения, проверьте совместимость.
2. Когда решения действительно реализованы, нажмите **«Зафиксировать корзину как реализованную»**.
3. Меняйте стадию, профиль и состав новой корзины. Исходная реализация сохраняется отдельно.
4. Рекомендации, корзина и итоговый план показывают тип перехода, диапазон трудозатрат и сложности интеграции.
5. После выполнения изменений можно повторно зафиксировать корзину: она станет новой основой.

Фиксация не происходит от простого добавления метода. Хранятся текущий профиль, черновая корзина и одна реализованная основа в `sessionStorage`: обновление страницы их сохраняет; новый независимый сеанс начинается с пустой основы. Изменение основы входит в отпечаток расчёта, отменяет устаревший запрос и требует пересчёта.

| Сценарий | Оценка перехода |
|---|---|
| Метод сохранён, значимые технические условия те же | Повторные трудозатраты и сложность внедрения — 0; стадия сама по себе ничего не переписывает |
| Изменён значимый параметр или версия движка | Проверка адаптации; нижняя граница может быть 0, если хватает существующего запаса |
| Заменяются два метода с явной связью альтернативы | Локальная настройка, изменение реализации или подсистемы — по уровню исходного и нового решений |
| Из одной функции удалён старый метод и добавлен новый, но связь неизвестна | Возможная замена с явной неопределённостью; необходима проверка интерфейсов |
| Сменён движок | Сценарий переноса архитектуры, кода, ассетов и данных |
| Удалена зависимость сохранённого метода | Повторная оценка адаптации зависимого метода, включая транзитивные зависимости |
| Метод удалён из новой корзины | Отдельно показаны отключение и проверка зависимостей; прежний аппаратный эффект не переносится |

Диапазоны трудозатрат — относительные экспертные баллы, не часы. Сложность интеграции имеет диапазон 0–5 и отделена от постоянной сложности самого метода. Одна анкета не позволяет установить, что придётся переписать **весь проект**: для такого вывода нужны сведения об интерфейсах, форматах, существующем коде и доступных средствах конвертации.

Аппаратная модель использует новый состав корзины. Накопленные трудозатраты, возраст проекта и сложность миграции не становятся множителями CPU/GPU. Допуск сложности ограничивает новые рекомендации, но не удаляет вычислительную работу уже выбранного метода.

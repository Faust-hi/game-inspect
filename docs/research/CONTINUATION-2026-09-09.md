## 3. Windows, Linux и фоновые процессы

### 3.1. Текущее поведение

В `hardware._memory_components` уже есть компонент `system: RAM=2.5, VRAM=0`. Поэтому прежнее утверждение «ОС вообще не учтена» было бы неверным. Однако:

- системная константа одна для Windows и Linux;
- отдельно не выражены desktop/compositor, фоновые приложения и их GPU-память;
- нет явного запаса CPU/GPU для конкурирующей работы;
- `platforms` не меняет `build_model`; ОС преимущественно проверяется как принадлежность области прогноза;
- `render_api` не связан строгой проверкой с выбранной ОС: Linux+DX12, Linux+Metal и Windows+Metal принимаются схемой и доходят до расчёта;
- `memory_model=dedicated/unified` даёт одинаковые компоненты, хотя организация физической памяти различается;
- общий результат для двух ОС не объясняет, какая конфигурация удовлетворяет каждой цели.

В свежем широком профиле Windows и Linux дали одинаковые CPU/GPU-индексы **0.9718 / 1.1829**, RAM **11.0** и VRAM **8.8** в текущих единицах модели. Это наблюдение о коде, не сравнительный benchmark операционных систем.

### 3.2. Как должны различаться сценарии

| Аспект | Windows | Linux | Правило MVP |
|---|---|---|---|
| Запуск | Нативная Windows-сборка | По умолчанию нативная Linux-сборка | ОС означает целевую сборку, а не ОС компьютера, на котором открыт анализатор |
| Графический путь | DirectX либо поддерживаемый движком Vulkan/OpenGL | Поддерживаемый конкретной версией движка Vulkan/OpenGL | Проверять сочетание ОС + движок/версия + API + возможность GPU |
| Windows-игра на Linux | Не относится к нативной Windows-оценке | Возможен Proton/Wine, но это другой путь | Не угадывать Proton по выбранному DX12. В MVP пояснить выход за нативный сценарий; не назначать универсальные −/+20% |
| Драйвер и функции | Поддержка зависит от GPU и драйвера | Поддержка зависит от GPU, драйвера и renderer | Наличие названия карты или общего API не подтверждает все расширения/технологии |
| RAM и VRAM | ОС, службы, desktop, другие программы | Ядро, desktop/compositor, службы, другие программы | Резерв присутствует в обоих сценариях; Linux не получает автоматическую «бесплатную» память |
| Производительность | Конкретный runtime, driver и сборка | Конкретный runtime, driver и сборка | Не задавать универсальное преимущество одной ОС; отличать совместимость от скорости |
| Две целевые ОС | Отдельный расчёт | Отдельный расчёт | Показывать оба результата; общая рекомендация удовлетворяет обоим по ресурсам и возможностям, а не является средним |

Valve прямо описывает Proton как путь с переводом DirectX в Vulkan и указывает зависимость результата от качества исходной реализации. Это не основание для фиксированного коэффициента «Linux медленнее». [Steamworks: Graphics](https://partner.steamgames.com/doc/steamhardware/recommendations?l=german&language=english).

В актуальной документации Unreal для Linux указан Vulkan RHI и условия отдельных графических возможностей. Приведённые там требования рабочего места разработчика/редактора, включая объём RAM, **нельзя переносить в минимум любой игры**. [Epic: Linux Development Requirements](https://dev.epicgames.com/documentation/unreal-engine/linux-development-requirements-for-unreal-engine).

В текущем API поле `render_api` одно. Для MVP при выборе двух ОС `auto` должен разрешаться отдельно по платформам; явно заданный API проверяется для каждой. Несовместимость одной цели выводится с её названием, а не исправляется незаметной заменой. Metal удаляется из рабочего PC-ввода. Неподдерживаемая комбинация не получает отметку «подходящее оборудование», но допустимые цели продолжают получать численный расчёт.

### 3.3. Что означает «фон всегда есть»

Даже без открытого браузера работают ОС, драйверы, службы и desktop. Но **наличие процессов не равно постоянной загрузке CPU на заданный процент**: процессы могут ожидать события, а активная работа конкурирует за время исполнения. Приоритет игры не отменяет системную обработку и I/O. [Microsoft: Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities).

Для MVP нужен один понятный сценарий по умолчанию: обычный рабочий стол и лёгкий фон, без параллельного рендера видео, компиляции, записи/стриминга и тяжёлых обновлений. Не требуется сканирование процессов пользователя, телеметрия или новая обязательная анкета.

Предлагаемое **стартовое экспертное допущение для последующей реализации**, одинаковое для обеих ОС до отдельных замеров:

| Резерв | Начальное допущение | Смысл |
|---|---:|---|
| RAM ОС, драйверов и desktop | 3 GiB | Заменяет существующий системный компонент 2.5, а не прибавляется поверх него |
| RAM лёгких фоновых приложений | 1 GiB | Условный launcher/связь и сопутствующие процессы |
| Выделенная VRAM desktop/других приложений | 0.5 GiB | Отдельно от ресурсов игры; не переносить как выделенную память на UMA |
| Запас производительности CPU | 10% | Игра не планируется на 100% условной доступной мощности |
| Запас производительности GPU | 5% | Условный запас для desktop/фона; не доказанный overhead драйвера |

**Эти числа не взяты из системных требований Windows/Linux и не являются измеренным расходом.** Это открыто обозначенная исходная настройка приближённого MVP. Совпадающий резерв не утверждает, что ОС одинаковы: он позволяет не выдумывать выигрыш Linux до проверки. При последующей калибровке резервы уточняются отдельно; дополнительный «страховой» множитель поверх них не вводится автоматически.

Для dGPU целевые соотношения:

```text
RAM компьютера >= уникальные RAM-ресурсы игры и runtime
                 + пиковые необходимые staging/копии
                 + резерв ОС + резерв фоновых программ

VRAM карты >= резидентные GPU-ресурсы игры + её пиковые буферы
              + резерв desktop/фона

доступная условная CPU-мощность = мощность кандидата × (1 - резерв CPU)
доступная условная GPU-мощность = мощность кандидата × (1 - резерв GPU)
```

Резерв производительности учитывается один раз при проверке кандидата. Он не меняет алгоритмический вклад выбранного метода и не превращается одновременно в фиксированные миллисекунды на каждой подсистеме. После измеренной калибровки нужно проверить, не включён ли тот же фон уже в используемый эталон.

Например, **условная** потребность игры с runtime 6 GiB RAM даёт 10 GiB вместе с предложенным резервом 4 GiB; результат нельзя округлить вниз до 8 GiB. Это арифметический пример применения допущения, не измерение игры.

### 3.4. Память, кэш и системные бюджеты

- В Windows игра должна ориентироваться на доступный ей бюджет видеопамяти, а не только на установленный объём. Превышение budget может вызвать вытеснение и заикания. [Microsoft: DXGI_QUERY_VIDEO_MEMORY_INFO](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/ns-dxgi1_4-dxgi_query_video_memory_info).
- В Vulkan `heapBudget` — меняющаяся оценка допустимого выделения, а `heapUsage` — оценка текущего использования. Поддержку расширения нельзя предполагать для любого устройства. [Khronos: VK_EXT_memory_budget](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceMemoryBudgetPropertiesEXT.html).
- В Linux `MemAvailable` учитывает возможность освобождения части кэшей; считать весь `Cached` безвозвратно занятым ОС неверно. Нельзя одновременно вычесть его из доступной памяти и снова добавить как полный системный расход. [Linux kernel: /proc/meminfo](https://docs.kernel.org/next/filesystems/proc.html).
- При UMA общие физические страницы CPU/GPU учитываются один раз. Отдельные копии и staging считаются дополнительно только там, где действительно предполагаются. Формула «RAM игры + вся VRAM игры» без проверки общих ресурсов неверна.
- Подкачка/SSD не заменяет недостающую RAM/VRAM без последствий. Дефицит — отдельный риск пауз; больше CPU/GPU не устраняет нехватку физической памяти.
- Размер установки игры, свободное место под её обновления/кэши и место установленной ОС — разные величины. `size_limit_gb` относится к игре; не прибавлять туда всю ОС.
- Пиковая компиляция PSO, распаковка или сохранение — другой режим, чем устойчивый кадр. В MVP объяснять риск пиков, не обещая неизменный FPS и не превращая пиковые временные данные в постоянно занятую память.

Эти APIs и метрики приведены как основание модели и будущей проверки. Реализовывать системный сборщик данных в текущем MVP не требуется.

### 4.1. Сквозные правила причинности

1. **Функция → базовая реализация → изменения от выбранных решений.** Нужно определить исходную работу. Нельзя одновременно добавить полный дорогой проход как функцию и второй раз как реализацию без вычитания заменённой части.
2. **Сцена → активная работа.** Размер мира, активные объекты, NPC и локальные виды не являются независимыми множителями одной и той же нагрузки. Пояснения анкеты должны определять, что считает каждое число.
3. **Разрешение → соответствующие проходы.** Не умножать AI на число пикселей; не уменьшать геометрию и submit общей скидкой апскейлера.
4. **Частота → соответствующая работа.** Физика, AI, сеть и отрисовка имеют разные частоты; принятую по умолчанию частоту показывать. Стабильный fixed timestep не гарантирует меньшую суммарную работу.
5. **Ограничение → проверка, а не сокращение потребности.** Невозможность уложиться в бюджет остаётся видимой; алгоритм не подставляет меньшие объёмы и заведомо недостаточное железо.
6. **Поздняя стадия → переработка и риск.** Архитектурная оптимизация не перестаёт физически работать на релизе; меняется цена её внедрения. Разные экраны не должны одновременно называть её запрещённой и учитывать как беспроблемно выбранную.
7. **Качество → конкретный компромисс.** Меньшая частота AI, упрощённая физика, отключённые эффекты и пониженное разрешение имеют разные последствия. Один показатель `quality_impact` не должен скрывать изменение игрового поведения.
8. **Объяснение → тот же итоговый расчёт.** Карточка показывает условный эффект, корзина — применённый эффект с перекрытиями, аппаратный итог — потребность с ОС/фоном. Эти величины связаны, но не одинаковы.

## 5. Реализации: заполнение, применимость и правильность эффектов

### 5.1. Как читать проверку 111 решений

Все текущие решения имеют запись в `METHOD_SUBSYSTEM_EFFECTS`; старый дефект распределения через отсутствующий `function_code` больше не описывает этот срез. Однако каталог содержит две разные оценки: скалярные `impact_*` для карточек/ранжирования и явную карту для аппаратного расчёта. Их знак, область и объяснение должны совпадать по смыслу.

В таблице ниже **числа переписаны из текущего кода**, а не предложены как исправленные или измеренные коэффициенты. CPU/GPU «−» означает экономию соответствующей работы; «+» — дополнительную работу. Для памяти знак показывает изменение компонента; одна запись `mem` сейчас одинаково масштабирует его RAM и VRAM. `rt_ms` — добавленное условное время на эталоне.

Статусы — инженерное заключение этого разбора:

- **Исправить** — обнаружено конкретное несоответствие механизму, области или способу применения эффекта.
- **Уточнить** — направление возможно, но нужен контекст исходной реализации, охват ресурсов или более подходящий источник; точный процент не подтверждён.
- **Без скидки / вне кадра / вне клиента** — отсутствие численного клиентского ускорения соответствует роли решения; нужные последствия всё равно должны объясняться.

Статус «Уточнить» не означает необходимость выключить весь расчёт. В MVP допустим явно обозначенный экспертный сценарий; нельзя выдавать условный коэффициент как гарантию для любой игры.

### 5.2. Ключевые уточнения механизмов по первичным источникам

**Разрешение и дополнительные виды.** Dynamic Resolution изменяет внутренний screen percentage в зависимости от GPU-нагрузки. Текущая карточка, уменьшающая только post-processing, не описывает этот механизм. Для split-screen нужно отдельно учитывать работу на вид и итоговую площадь изображения; четыре четверти одного экрана не обязательно означают четыре полноэкранных набора буферов. Второе — вывод для модели, а не универсальная формула конкретного движка. [Epic: Dynamic Resolution](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-resolution-in-unreal-engine).

**Streaming pool.** В Unreal `r.Streaming.PoolSize` относится к пулу текстур и перечисленных дополнительных ресурсов; есть отдельное ограничение временной памяти. Следовательно, правило «ввести pool как расход RAM, половину добавить к VRAM, затем ещё прибавить все текстуры» не следует из документации. Для междвижкового поля нужно собственное ясное определение. [Epic: Texture Streaming Configuration](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-configuration-in-unreal-engine).

**Сжатие нейронных текстур.** NVIDIA различает NTC-on-Load с транскодированием и NTC-on-Sample. В первом случае сокращение хранения не обязательно сохраняется в резидентной VRAM; во втором inference выполняется при обращениях и имеет вычислительную цену. Нельзя использовать одну скидку памяти и одновременно универсальную экономию shading для обоих режимов. [NVIDIA RTXNTC SDK](https://github.com/NVIDIA-RTX/Rtxntc).

**GC и pooling.** Повторное использование объектов может снижать стоимость создания/уничтожения и GC. Это не утверждение, что удерживаемый пул всегда занимает меньше памяти, чем исходный сценарий. Эффект должен зависеть от аллокаций и рабочей ёмкости пула. [Unity: Managed memory](https://docs.unity3d.com/Manual/performance-optimizing-code-managed-memory.html).

**PSO precaching.** Его задача — подготовить pipeline state и уменьшить compilation hitches; при этом расходуются время компиляции и память/кэш. Это другая характеристика, чем одинаковая экономия средних миллисекунд каждого кадра. [Epic: PSO Precaching](https://dev.epicgames.com/documentation/unreal-engine/pso-precaching-for-unreal-engine).

**Отражения.** SSR — экранное отражение; SSGI — непрямое освещение, и эти термины нельзя подменять. Planar reflection добавляет scene capture; стоимость зависит от сцены и настроек захвата. «Включить planar reflection» и «ограничить бюджет уже включённого отражения» имеют разные базовые варианты. [Epic: Screen Space Reflections](https://dev.epicgames.com/documentation/en-us/unreal-engine/screen-space-reflections-in-unreal-engine), [Epic: Planar Reflections](https://dev.epicgames.com/documentation/en-us/unreal-engine/planar-reflections-in-unreal-engine).

**VRS.** Variable Rate Shading управляет частотой shading и имеет аппаратные уровни поддержки. Ссылка карточки на Temporal Anti-Aliasing не является обоснованием VRS. [Microsoft: Variable Rate Shading](https://microsoft.github.io/DirectX-Specs/d3d/VariableRateShading.html).

Источники подтверждают механизмы и условия. Приведённые в каталоге проценты из этих страниц автоматически не следуют. Не требуется сохранять документы в новой базе приложения: достаточно корректной ссылки и краткого условия в существующей карточке/таблице.

Правило для MVP: связь `complement` объясняет функциональное дополнение и сама по себе не даёт коэффициент. Для экономии одной и той же работы — наибольшая обоснованная экономия; самостоятельные дополнительные расходы сохраняются. Если один ресурс заменяется другим, сначала описывается замена, затем объединяются расходы.

Текущая ветвь памяти нарушает это правило: `min(mem_delta)` может выбрать меньший добавочный расход и потерять остальные. Например, прежняя изолированная проба с компонентом 10: VSM → 12.5, static shadow caching → 10.8, вместе без complement → 10.8. Код этой ветви повторно просмотрен; математическое исправление нельзя свести к безусловной сумме без определения общих/заменённых ресурсов. Доказательство исходной пробы сохраняется в [FINDINGS.md, R02](FINDINGS.md).

Жёсткая несовместимость означает невозможность одновременного выбранного способа исполнения в данном контексте. Ухудшение качества, риск задержки, дополнительные расходы и отсутствие проверки не являются её синонимами. Альтернативы для одной работы требуют выбора; для разных объектов/проходов их совместное использование может быть допустимо. Для MVP достаточно исправить эти 20 записей и существенные общие эффекты, без построения универсального графового движка.

### 6.3. Связи с инструментами движков

Предыдущий индекс содержит 473 связи с инструментами семи движков. Полная декартова развёртка на версии не становится обязательным планом работ. Приоритет — связи, реально показываемые для выбранного движка/версии и существенно меняющие применимость.

Повторно подтверждено: `virtual_geometry_clusters` учитывается для Unreal 4.27 так же, как для 5.5. Общий алгоритм кластерной геометрии не равен встроенному Nanite; для старой версии можно обсуждать собственную реализацию, но нельзя показывать недоступный встроенный инструмент как готовый. Ссылки инструментов и конкретных связей сейчас в seed совпадают. Сериализация при этом не сохраняет отдельный `MethodEngineLink.source_url`, когда он отличается от URL документации инструмента. Это небольшой вопрос существующего контракта, не основание для отдельной provenance-системы. Исправление допустимо обычным полем источника и текстовым условием.

| Рекомендации | Альтернативы сравниваются внутри одной функции; балл — предпочтение по выбранным весам | Группировка уже есть. TOPSIS остаётся относительным: добавление альтернатив может менять порядок; не называть балл процентом ускорения или доказательством правильности |
| Стадия и план | Показать стоимость поздней переработки и последовательность внедрения | Избежать безусловного запрета всей архитектуры после alpha; выбранная рабочая реализация не исчезает из физической модели от даты |
| Корзина | Видны выбранные, учтённые, конфликтующие и исключённые методы с причиной | Сохранять текущий снимок ответа в памяти для согласованности экранов; не развивать историю пользовательских версий |
| Риски | Выводятся из фактического набора, условий и результата | Наличие 4K/high не делает upscaling обязательным; отсутствие конкретного world_partition_streaming не доказывает отсутствие любой потоковой загрузки |
| Мягкая совместимость | Риск качества/латентности объясняется как риск | `conflict_map` включает risk вместе с hard_conflict, а общий текст может назвать их взаимоисключением; согласовать формулировки |
| Ограничения памяти | Сравнить физический лимит с полной потребностью, включая ОС/фон | Текущие потребности не уменьшаются от лимита — правильно; смысл лимита и резервы требуют явного определения |
| CPU | Проверять последовательную работу и общую производительность; распараллеливание ограничено | ST/MT уже используются. `PARALLEL_SPEEDUP=2.4` — экспертная модель; jobs не должны получать необоснованную вторую экономию |
| GPU raster/RT | Проверять возможности, VRAM и совместную стоимость реального GPU-кадра | Два отдельных порога могут дать каждой части весь бюджет кадра. Нельзя безусловно трактовать raster и RT как независимые устройства, полностью работающие параллельно |
| Узкое место | Назвать доминирующую нагрузку условного эталона либо считать доли на выбранных кандидатах | `_bottleneck` сравнивает эталонные индексы, а не загрузку конкретных выбранных CPU/GPU. Название не должно обещать диагноз реальной машины |
| Память | Состав уникальных ресурсов, временных копий, игры и системы | Теряются дополнительные mem-расходы; единый коэффициент компонента затрагивает RAM и VRAM одинаково; UMA не моделируется |
| Накопитель | Отдельно installed size, I/O и свободное место под операции | `_estimate_install_size` оценивает диск через резидентные GPU-ресурсы. Установка и resident set имеют разный состав |
| Сеть и диск в сводке | Чётко отличать экспертный балл от байтов/ГБ/скорости | `aggregate_load` суммирует `impact_network/disk × 0.08`. Это не подсистемная модель трафика/размера и может расходиться с аппаратным объяснением |
| Уверенность | Обозначение полноты входа/допущений, без ложной статистики | `confidence` начинается с 0.85 и уменьшается эвристически. Не показывать как вероятность попадания в ±70% |
| Администрирование | Исправлять/публиковать знания и сохранять связь с расчётом | Импорт справочников допустим. Не возвращать пользовательские проекты, примеры игр или паспорта |
| Сверка с практикой | Одна заглушка | Не добавлять действующий endpoint/score ради завершения текущей редакции |

Для GPU минимальная безопасная трактовка следующей реализации: последовательные растровые и RT-проходы складываются в бюджет **на одном кандидате**, а известное перекрытие учитывается только отдельно обоснованной долей. Сравнение CPU и GPU как разных частей конвейера не даёт права бесплатно перекрывать все задачи внутри каждого устройства.

Для сетевых/дисковых последствий в MVP достаточно честной качественной оценки и конкретного объяснения. Не нужно изобретать Mbps или ГБ из суммарного балла. Численные требования CPU/GPU/RAM/VRAM при этом сохраняются.

### 9.3. Что остаётся следующей проверкой точности

Нужны сопоставимые реальные сценарии игры, настройки, сборки и измерения. Внешние партии могут помочь выбрать такие сценарии, но не являются готовой калибровкой. Достаточная конфигурация из системных требований — верхняя оценка достаточности, а не измеренный минимальный CPU/GPU.

Метрику ±70% следует считать отдельно для CPU/GPU по согласованным эталонам, а не по расстоянию моделей в списке или совпадению названий. Числа confidence, рейтинг TOPSIS и предел экономии подсистемы 0.70 не заменяют эту проверку.

Для текущего MVP обязательны понятный численный ориентир, причинная согласованность параметров и решений, учёт ресурсов ОС/фона и честные последствия выбора. Полное закрытие внешнего корпуса и отдельная система хранения историй в эту приёмку не входят.

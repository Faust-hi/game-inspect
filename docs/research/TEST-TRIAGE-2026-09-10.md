## 3. Активный контур (§2 плана) — состояние

Присутствует и соответствует требованиям плана:

* **Старт** (`_bootstrap`): миграции вместо `create_all`, отказ при неподдерживаемой
  СУБД, первичное заполнение пустой базы, синхронизация классификации.
* **Готовность** (`/api/health`): `ready` / `degraded` / `unavailable`, отдельно —
  `schema_error`, счётчики опубликованных методов и железа.
* **Расчёт**: неизвестные коды → риски, исключённые решения — с причиной,
  конфликты/зависимости/синергии корзины, `unmet_limits`, `modeling_gaps`,
  `confidence` < 1 и `caveats`, `exceeds_catalog`.
* **Ошибки**: единый формат `{error, details, code, request_id}` плюс заголовок
  `x-request-id`; подробности исключений клиенту не передаются.

Полный pytest и браузер при обычном запуске не выполняются — это зафиксировано
и в коде, и в README.

## 5. Найденные дефекты самих проверок

### 5.1 Вакуумная проверка целостности каталога

`backend/tests/test_demo_stability.py`, `test_published_slice_has_sources_and_no_dangling_links`:

```python
assert link["a_code"] in codes or link["a_code"], link
assert link["b_code"] in codes or link["b_code"], link
```

При непустом коде второе условие истинно всегда, поэтому оборванная связь
конфликта **не обнаруживается**. Инвариант из §4 плана заявлен, но не работает.
Требуется переписать на строгое вхождение в множество кодов.

### 5.2 Тест, копирующий формулу реализации

`test_combined_effects.py::test_raster_and_rt_share_one_frame_budget` сравнивает
`required_gpu_index` с `(raster + rt) / budget` — это формула реализации.
По §3 плана ожидаемое должно следовать из независимого правила: «требование к
GPU учитывает оба прохода, а не только более тяжёлый».

### 5.3 Проверка приватной функции

`test_hardware_bottleneck.py::test_zero_means_empty_not_missing` вызывает
`app.services.hardware._load_indices`. Свойство «явный ноль дешевле
неизвестности» существенно, но проверять его нужно через API.

## П2.2 Браузерный контур проверяет устаревшую сборку

`e2e_server.py` поднимает `app.main:app`, который раздаёт `frontend/dist`.
Сборка в репозитории была от 09.09 14:46 при исходниках от 10.09 09:06 —

То есть браузерная проверка молча тестирует старый код. Перед показом
обязательна пересборка; иначе контур не защищает, а создаёт ложную уверенность.

dev-сервера.

## П2.3 SPA-fallback перехватывает неизвестные пути API

При собранном `dist` регистрируется маршрут `/{full_path:path}`, поэтому
`GET /api/catalog/nonexistent` возвращает **200 text/html** — главную страницу
приложения, а не 404. Ошибка в адресе запроса маскируется: клиент получает
«успешный» ответ, который не удаётся разобрать. `POST` на неизвестный путь
даёт корректный 405 JSON, то есть проблема только для GET.

## П3.5 П2.5: разбор 13 методов без связей с инструментами

Снято с заполненной базы. Все 13 — опубликованные методы:

| Метод | Функция |
|---|---|
| `ai_director_pacing` | Поведенческий ИИ NPC |
| `audio_convolution_reverb` | Аудиосистема |
| `cloth_baked_animation`, `cloth_constraint_simulation` | Симуляция ткани |
| `runtime_fracture_budget` | Разрушения |
| `hair_cards_lod`, `hair_strand_simulation` | Волосы |
| `lag_compensation_rewind`, `subtick_networking` | Сетевой код |
| `directstorage_io` | Потоковая загрузка |
| `portal_scene_capture_budget` | Порталы |
| `async_compute_overlap` | Архитектура рендера |
| `runtime_security_budget` | Античит |

**Отсутствие связи у всех 13 обосновано, данные не потеряны.** Это решения,
которые не опираются на встроенный инструмент конкретного движка: сетевой код
и античит реализуются поверх движка, DirectStorage — платформенный API,
а остальные — приёмы уровня движка в целом. Показательно, что
`directstorage_io` вообще не должен иметь связи с инструментом: его условие —
платформа, и оно уже проверяется тестом `test_platform_condition_directstorage`.

Значит, настоящий дефект не в данных, а в неразличимости состояний:
`engine_support = null` сейчас означает и «метод не зависит от инструмента
движка», и «данных нет». Пользователь не может их отличить, а предупреждение
сида («нет связей с инструментами») перестанет быть правдой, если объявить
все такие методы независимыми.

Требует предметного решения, а не правки проверок. Варианты:

1. Явный признак «не зависит от инструментов движка» в данных метода
   (поле + миграция + пояснение в карточке). Честно, но меняет схему.
2. Дописать связи там, где аналог в движке действительно есть
   (ткань, волосы, разрушения), остальных пометить признаком из п. 1.
3. Оставить как есть, но показывать в карточке «привязка к версии движка
   не указана» вместо пустоты — минимально и ничего не утверждает.

Без выбора предметной позиции правка превратилась бы в догадку, поэтому
изменений не внесено.

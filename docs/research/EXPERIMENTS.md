## Физическая память: разрешённые формулы

Для непрерывной полезной нагрузки несжатой 2D-текстуры:

`payload_bytes = Σ_m max(1, width >> m) × max(1, height >> m) × bytes_per_texel × layers`.

Для BC1 каждого mip: `ceil(w_m/4) × ceil(h_m/4) × 8 × layers`. Для других block formats размер блока должен приходить из спецификации формата [S06]. Для полного mip-набора квадрата power-of-two множитель около 4/3 — следствие суммы размеров уровней, не универсальная стоимость памяти движка. В малых BC-уровнях действует минимум блока.

Результат E06:

- RGBA8 1920×1080: 8 294 400 bytes полезной нагрузки одного изображения.
- RGBA8 3840×2160: 33 177 600 bytes, ровно в четыре раза больше.
- RGBA8 4096×4096 со всеми mip: 89 478 484 bytes.
- BC1 4096×4096 со всеми mip: 11 184 824 bytes.

Из этого нельзя выводить, что 1.8 GB render_targets модели должны равняться одному framebuffer. Для полного расхода нужны все attachments/history/shadow maps, форматы, sample count, transient/aliasing, buffering, heap alignment и lifetime. Для MSAA учитывать число samples конкретного attachment плюс resolve target, если он существует; не умножать память всей игры на MSAA.

## Обязательные будущие измерительные протоколы

Общий паспорт: система и версии ОС/driver/build/API; CPU/GPU и power/clock limits; объём/каналы/частоты RAM; выделенная/общая память; разрешения output/internal и настройки; сцена/камера/seed; длительность; число кадров; версии инструментов. Сохранить сырые frame/tick timestamps и ресурсы. Условия охлаждения и фоновые задачи фиксировать как наблюдение.

Один предварительный прогрев, затем минимум пять повторений каждого варианта. Для cold-load отдельно определить очистку/состояние кэша; не называть тёплый повтор холодным. Порядок A/B сбалансировать, чтобы прогрев/троттлинг не совпал с выбранной оптимизацией. Не смешивать миллионы зависимых кадров с миллионами независимых экспериментов.

| Группа плана | Малый эксперимент | Условия и метрики | Что останется недоказанным |
|---|---|---|---|
| Постоянная память | Минимальная сцена в доступной сборке движка, один пустой/один наполненный вариант | Процесс RAM, resident/committed, GPU allocations и peak отдельно, одинаковая release-сборка | Нет установленного движка — записать protocol_only; не устанавливать большой пакет обязательно |
| Графические ресурсы | Генератор дескрипторов textures/attachments; при доступном API измерить footprints | Сопоставить аналитические bytes и API placement requirements; известные formats/MSAA/mips | Без GPU allocation не утверждать resident и overhead |
| Интенсивность | Матрица независимых геометрии/материалов/света/активных тел/AI tick | Менять один фактор, потом явно выбранные взаимодействия; main/render/worker/GPU timings | Одинаковый object count не гарантирует эквивалентность сцен |
| Методы | meshoptimizer на фиксированных мешах; instancing/culling на контролируемой сцене | Геометрическая ошибка, размер, cache/overdraw proxy; runtime CPU/GPU только при реальном рендере | Proxy-метрика не равна FPS. Commit/build/input hash обязательны до запуска |
| Взаимодействия | A, B, A+B, baseline; отдельно перестановки и тройки | Work/resource identity, visibility, quality, память, timing | Нельзя вывести синергию только из суммы двух отдельных экспериментов |
| Каталог | Сопоставимые сцены на нескольких CPU/GPU, включая iGPU | Стабильный build, независимая шкала, base FPS, memory capacity и compatibility | Один аппаратный score не гарантирует переносимость между raster/RT и CPU bottlenecks |

PresentMon применим к Windows, Tracy требует подходящей интеграции; Linux-протокол нужно отдельно привязать к доступному инструменту/версиям. В этой работе ни одна из этих интеграций не выполнялась.

## Выборка и метрики

58 профилей и 980 строк не являются 58 независимыми измерениями CPU/GPU. `validation/report.json` содержит 58 ineligible-сценариев и нулевое paired coverage. Новые численные эталоны этим исследованием не добавлены.

Четыре страты: лёгкие/тяжёлые исторические и современные сценарии. Отдельные подгруппы CPU, graphics, memory, streaming. Возраст должен описывать версию/build, а тяжесть — наблюдаемую работу/ограничение, а не вычисленный этим же MVP класс. До использования страт нужно определить границы, иначе метрики произвольно меняются от разметки.

Все версии/сцены одной связанной игры группировать при разделении train/validation/test. Источники, уже просмотренные при настройке, не называть слепым holdout. Исправление фактов партий допустимо только отдельной аннотацией в исследовании; сами файлы партий не изменяются.

Для point-reference: `signed_error = (P_pred - P_ref)/P_ref`, `absolute_relative_error = abs(signed_error)`, при `P_ref > 0` и общей независимой шкале. Совместное попадание — CPU и GPU каждый ≤0.70. Память и совместимость отдельно. Условные интервалы оцениваются покрытием, шириной и корректностью предпосылок; не заменять их искусственно средней точкой. sufficient-reference не даёт нижнюю границу и не доказывает точность минимума.

Публиковать paired coverage, пропуски с причинами, signed bias, median/P90 и размер каждой страты. Не вычислять P90 точности по неподтверждённым требованиям магазина. Обязательная доля успеха пользователем не задана; цель ±70% не достигнута самим фактом наличия этой формулы.

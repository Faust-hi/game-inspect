# Предварительная спецификация будущих изменений

**Статус: исследовательский проект спецификации, не готовая к реализации окончательная спецификация по пункту 6 плана.** Нерешённые вопросы перечислены в конце. В этой работе ничего из предложенного не реализуется. Указанные контракты — предложения, не описание текущего API.

## Зафиксированные решения

1. Сохранить локальное SQLite-приложение и короткую анкету; количественная область Windows/Linux PC. Отдельные внешние исследовательские инструменты не включать в runtime.
2. Не использовать год/название игры как поправку. Профиль нагрузки описывает работу и реализацию, а hardware scale — наблюдаемую стоимость этой работы.
3. Не выпускать числа без основания. Для неизвестных параметров допускать именованные условные сценарии только с подтверждёнными границами; иначе `not_estimated` с конкретными причинами.
4. Существующие экспертные coefficients не повышать до статуса эмпирических. Исторические результаты сохранять с прежней версией и маркировкой, не пересчитывать молча.
5. Игровой baseline должен указывать уже реализованные оптимизации. Перспективная корзина изменяет этот baseline; наличие функции/названия технологии не начисляет повторную экономию.

## Предлагаемые контракты

Значение параметра: `value`, `unit`, `state`, `origin`, `source_ids`, `assumption_id`. Допустимые состояния: `known`, `unknown`, `not_applicable`; default — отдельное происхождение, не known measurement. Ноль допустим только при физическом смысле и валидации поля. auto — инструкция выбора, результат выбора записывается как допущение/разрешённая конфигурация.

Для сценария хранить: платформу/ОС, engine version, renderer/pipeline, render API, клиент/сервер/host, output/internal resolution, target base FPS, optional display/FG config, baseline implementations, уже включённые методы. Для тонких параметров (geometry/material/light intensity, simulation frequency, resource footprints) отсутствие значения разрешено, но ограничивает численную оценку.

Эффект метода: `method_id`, `implementation_id`, `phase`, `execution_role`, `resource`, `target_work_ids` или `target_resource_ids`, `operation`, `preconditions`, `evidence_ids`, `validity_domain`, `quantitative_model_id` либо `null`. Статический балл impact не является процентом. Список эффектов допускает CPU/GPU/runtime/build/memory последствия одновременно.

Операции следует различать: добавление работы/ресурса, замена существующей реализации, удаление доказанно избыточной работы, перенос ресурса/этапа. Для overlap без определённых общих work IDs количественное объединение запрещено. Default «взять максимум экономии» также является допущением и не гарантирует консервативность при новых накладных расходах.

Связь: `a_id`, `b_id`, `type`, `direction`, `conditions`, `engine_version_range`, `pipeline`, `platform_scope`, `affected_resources`, `evidence_ids`, `review_status`, `consequences`. Типы разделяют обязательную зависимость, взаимоисключение, альтернативу, риск, перекрытие, функциональное дополнение, измеренный совместный эффект и неизвестность.

Условия должны быть типизированными предикатами, не исполнением произвольной строки: поле/оператор/значение, композиции all/any/not с ограниченной глубиной. Результат оценки условия трёхзначный: true/false/unknown. Unknown не доказывает применимость и не даёт количественную экономию; карточка остаётся доступной для уточнения.

Результат: `schema_version`, `algorithm_version`, `catalog_revision`, `input_snapshot`, `normalized_input`, `assumptions`, `scenarios`, `included_effects`, `excluded_effects`, `compatibility`, `evidence_ids`, `limitations`. Для каждой численной величины статус и единица; `not_estimated` возвращает `null`, а не ноль/минимальную модель из каталога. Причины: insufficient_inputs, uncalibrated_model, unknown_compatibility, unsupported_platform, outside_validity_domain, catalog_gap.

Идентификатор причины и русское объяснение должны доходить одинаково до UI, API, сохранения и экспорта. Пользователь видит конкретный недостающий параметр, а не внутреннее имя класса. Численный confidence не отображается как вероятность точности без отдельной калибровки.

## Модель расчёта и границы модулей

Предлагаемые ответственности: нормализация входа; оценка условий/графа; построение сценариев работ и ресурсов; аппаратное отображение; подбор конфигураций; объяснения; ранжирование. Разделение функций по ответственности должно предшествовать механическому разбиению большого файла. Не вводить plugin framework, DI-контейнер или ML-сервис только ради этого разделения.

Бюджет базового кадра: `1000 / base_fps` ms. Средняя стоимость задачи фиксированного такта: `cost_per_tick_ms × tick_hz / base_fps`, только если стоимость шага известна, режим устойчив, и отдельно учитывается накопление шагов. Эта формула не даёт стоимость AI/физики из одного числа NPC.

Стоимость CPU определяется работами, зависимостями и планированием. Однопоточный и многопоточный score должны иметь указанный benchmark/аппаратную шкалу; фиксированный PARALLEL_SPEEDUP нельзя принять без измерений. Для GPU raster/RT отдельно проверяются функциональная возможность и общая стоимость графа проходов: прохождение каждого независимого порога не доказывает, что их совместная работа укладывается в кадр.

Память определяется ресурсами и временем жизни: логические bytes, размещённые bytes, резидентность и peak — разные показатели. Пик не равен сумме пиков ресурсов, если они не живут одновременно. При неизвестной стратегии residency/aliasing нельзя выдавать точное потребление. Постоянный бюджет ОС допустим только как явно выбранное условие среды с источником, не свойство всех игр.

Для оборудования сначала проверяется версия API/features и память конфигурации, затем производительность на допустимой измеренной шкале. Отсутствующая ёмкость iGPU означает unknown configuration; отсутствие кандидата в ограниченном каталоге — catalog_gap/unknown, а не вывод о невозможности запуска вообще. Совместимость CPU/платы/RAM требует отдельной модели конфигурации; список двух названий CPU/GPU ещё не комплект компьютера.

## Ранжирование

Сначала отделить функционально неподходящие варианты и условия, затем сравнивать способы решения одной задачи. Текущее группирование по функции сохранить как полезное основание. Корзина — отдельный объект со своими конфликтами, ресурсами и последствиями; сумма TOPSIS scores не имеет установленного смысла.

Экспертные performance_gain, quality, concept, implementation_cost, late cost, risk, resource_fit и confidence требуют паспортов шкал и весов. Текущий risk вычисляется из complexity: это не независимая оценка риска. Нельзя утверждать, что confidence всё ещё входит в risk — прочитанный код использует другую формулу. Изучить корреляцию со стоимостью и санкции stage, а не удалять критерии автоматически.

Обязательные проверки: одиночная/вырожденная группа, перестановка вариантов, dominated addition/removal, изменение весов и шкал, tie cases, смена набора после применения условий. Не объявлять порог 0.02 научно обоснованным на основании малого разброса выходов самой модели. Окончательный выбор между относительным TOPSIS и фиксированными опорными шкалами остаётся открытым до исследования критериев; это блокер окончательной спецификации.

## Совместимость и миграции — требования к последующей детализации

Сохранять старый сериализованный snapshot без выдуманного заполнения отсутствующих полей. Новая версия профиля должна различать historical default и введённое значение. При пересчёте создавать новый результат с новыми версиями, оставляя старый доступным для сравнения.

Для SQLite требуется версионированная миграция через существующий механизм, с резервной копией и проверкой старого снимка. Предполагаются отдельные записи evidence/claims, эффекты и условия, ссылки на неизменяемые версии каталога. Конкретная DDL и номер миграции не назначены: сначала завершить инвентаризацию текущих migration/API/export путей. Это явно незавершённая часть, не инструкция implementer самостоятельно выбрать схему.

## Что блокирует окончательную спецификацию

Не завершены индивидуальная проверка 980 строк и источников всех методов/движковых связей; сквозная проверка каждого публичного поля, импорта/экспорта/истории; текущий статус всех D/G/N; определения аппаратных шкал и данных для сценарных границ; решение по шкалам TOPSIS; точная совместимая SQLite-схема. До их закрытия этот документ нельзя маркировать ready-for-implementation или выдавать за полностью выполненный план.

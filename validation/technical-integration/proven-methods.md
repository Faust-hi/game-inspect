- Что это (конкретный техметод): отдельная compute-очередь (ACE) крутит compute (пост, bloom, тонемап, culling) пока graphics-очередь занята геометрией/шейдингом; синхронизация timeline/binary семафорами, без `COMPUTE->FRAGMENT` stalls.
- Источники: Khronos `Vulkan Samples async_compute` (21.8 vs 22.9 мс, fragment starvation лечится); Khronos Tutorial `Asynchronous Compute Orchestration` (ACE + queue families + Sync2); ARM Mali Blog `Using async compute on Mali` (темпераментная оптимизация последних процентов, мерить обязательно); партии `async_compute_vulkan | +30-66% на GCN`, `shaders_dx12_async_compute`.
- Доказательство как проверить: счётчики `fragment cycles vs GPU cycles`, вкл/выкл async queue + double-buffer HDR прогон. [RenderDoc, PIX, Unreal Insights, Arm Mobile Studio] | confidence 0.75
- Шаги: Вынести bloom/тонемап/culling в compute. / Развести очереди + семафоры без блокировки fragment. / Прогнать TBDR vs IMR кейсы отдельно.
- Влияет: GPU -1 (перекрытие) CPU 0 | качество 0
- Плюсы: Заливает дыры таймлайна; На GCN/консолях — десятки процентов
- Минусы: Борется за те же шейдерные ядра; На TBDR легко задушить; Сложная синхронизация
- Ограничения: Не масштабируется бесконечно; Партийные `+30-66%` — наблюдение idTech6/GCN, не гарантия под твою сцену | Условия: Нужен `pso_precaching`-порядок и профайлер, иначе регресс
- Связь с `tiled_clustered_light_culling`/`pso_precaching_warmup` [complement/independent]: каждый проход своей ценой, общей скидки нет.
- Почему этот, а не другой: в `rendering_architecture` альтернативы `hiz_software_occlusion`, `tiled_clustered_light_culling`, `srp_batcher_discipline` — те режут работу, async перекрывает оставшуюся. Выбор: fragment голодает — async; вызовов много — batcher/culling.

# Информационная система поддержки принятия решений по оптимизации разработки игр

Система помогает ещё **до появления проблем производительности** выбрать способ реализации
игровых функций, получить объяснимое ранжирование вариантов, увидеть их совместимость
друг с другом и оценить референсный минимальный класс оборудования.

Главный принцип: **каждая рекомендация объясняется, опирается на источник и зависит от
конкретного проекта**, а не выдаётся как универсальный совет.

---

## 1. Быстрый запуск

Требования: Python 3.11+, Node.js 18+. Установка СУБД не требуется — по умолчанию
используется локальный файл SQLite.

### Windows

```bat
start.bat
```

Скрипт создаёт виртуальное окружение, устанавливает зависимости, поднимает backend на
`http://127.0.0.1:8000` и frontend на `http://localhost:5173` в отдельных окнах консоли,
после чего открывает приложение в браузере. Окна консоли можно закрыть для остановки.

Отдельные запуски, если окружение уже подготовлено: `backend\run.bat` и `frontend\run.bat`.

### Вручную

```bash
# Backend
cd backend
python -m venv ../.venv
../.venv/Scripts/python.exe -m pip install -r requirements.txt
../.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# Frontend (в отдельном терминале)
cd frontend
npm install
npm run dev
```

При первом запуске backend автоматически создаёт схему и заполняет базу
демонстрационными данными (`AUTO_SEED = true`). Повторный запуск не дублирует записи.

Полезные адреса:

| Адрес | Назначение |
| --- | --- |
| `http://localhost:5173` | пользовательский интерфейс |
| `http://127.0.0.1:8000/api/health` | состояние сервиса |
| `http://127.0.0.1:8000/api/docs` | интерактивная документация API (Swagger) |

### Переход на PostgreSQL

```bash
DATABASE_URL=postgresql+psycopg2://user:password@localhost:5432/gamedev_dss
```

Переменные окружения можно задать в файле `backend/.env` (см. `backend/.env.example`).

```

│   │   ├── models/           ORM-модель и перечисления предметной области
│   │   ├── schemas/          Pydantic-контракты запросов и ответов
│   │   ├── services/         вычислительное ядро
│   │   │   ├── rules.py      фильтрация недопустимых решений и риски
│   │   │   ├── topsis.py     многокритериальное ранжирование
│   │   │   ├── recommender.py  оркестрация расчёта и объяснения
│   │   │   ├── gower.py      поиск похожих игр (расстояние Гауэра)
│   │   │   └── hardware.py   оценка референсного класса оборудования
│   │   ├── api/              catalog / recommend / admin
│   │   └── seed/             наполнение базы инженерных знаний
│   └── tests/                pytest: алгоритмы, API, сценарии раздела 8
├── frontend/                 React 18 + TypeScript + Vite
│   └── src/screens/          экраны 1–11 раздела 7 плана
├── start.bat                 одновременный запуск backend и frontend
├── backend/run.bat           запуск только backend
├── frontend/run.bat          запуск только frontend
└── README.md
```

Стек: **FastAPI, SQLAlchemy, Pydantic, PostgreSQL (совместимо с SQLite), React, TypeScript.**
Импорт каталогов поддерживается из CSV и JSON.

## 3. Модель предметной области

Основные сущности и их связи:

| Сущность | Смысл |
| --- | --- |
| `GameFunction` | игровая функция — что именно должно работать в игре |
| `Method` | вариант реализации функции или общий метод оптимизации |
| `Engine` / `EngineTool` | игровой движок и его инструменты |
| `MethodEngineLink` | связь метода с инструментом движка (8 типов) |
| `Conflict` | конфликт, зависимость или усиление между методами |
| `GameExample` | подтверждённый пример из реальной игры |
| `HardwareCPU` / `HardwareGPU` | характеристики оборудования |
| `Project` | сохранённый профиль и результат расчёта |
| `ValidationIssue` | замечание проверки целостности базы |

Каждый метод и вариант реализации описан по полной схеме:

* уровень решения — **архитектура, производственный процесс, алгоритм, настройка**;
* рекомендуемый этап внедрения и стоимость позднего внедрения;
* влияние на CPU, GPU, RAM, VRAM, накопитель и сеть (шкала −2…+2);
* влияние на качество изображения и на исходную концепцию игры;
* способ расчёта — **real-time, предварительный, гибридный**;
* совместимость, конфликты и зависимости;
* способ последующей проверки решения.

Связь общего метода с инструментом движка имеет один из восьми типов:
прямая реализация, частичный аналог, альтернативный подход, дополнение, автоматизация,
диагностический инструмент, ограниченное применение, отсутствие встроенного аналога.

Материалы проходят состояния **черновик → проверено → опубликовано**.
В публичных рекомендациях участвуют только опубликованные записи с указанным источником —
это проверяется автоматически, в том числе тестами.

Схема не ограничивает число форматов, движков и методов: каталог расширяется через
административный раздел без изменения кода.

## 4. Как работает алгоритм рекомендаций

1. **Анализ проекта.** Профиль игры (формат, структура мира, стадия, движок, платформы,
   масштаб, число объектов и NPC, целевые разрешение/качество/FPS, бюджеты, приоритеты).
2. **Выявление рисков.** Отдельные риски проекта на текущей стадии разработки.
3. **Отбор решений** по выбранным игровым функциям.
4. **Исключение недопустимого** — решения, нарушающие обязательные ограничения
   (формат, платформа, сложность, отсутствующие возможности движка или оборудования),
   не попадают в рекомендации, но остаются видимыми с указанием причины.
5. **Учёт стадии разработки** и стоимости позднего внедрения.
6. **Ранжирование методом TOPSIS** по набору критериев с весами, зависящими от
   приоритета пользователя: качество, производительность, стоимость, сбалансированный.
7. **Объяснение** — у каждой рекомендации список причин и значений критериев.
8. **Связь с движком** — показывается, какой инструмент выбранного движка реализует общий
   метод, и чем его можно заменить.
9. **Предупреждения** о конфликтах и о возможном изменении концепции игры.

Пользователь добавляет решения в **корзину проекта**, после чего система пересчитывает
сводный профиль нагрузки и показывает совместимость набора. Полный перебор всех
комбинаций не выполняется — проверяется совместимость выбранного набора.

Каждое решение помечается одной или несколькими пометками:
рекомендуется · применимо при условиях · желательно внедрить сейчас ·
позднее внедрение затруднено · требует прототипирования · может снизить качество ·
может изменить концепцию · не рекомендуется.

## 5. Аппаратная оценка

По каталогу хранятся модель и поколение, архитектура, класс производительности,
объём и пропускная способность памяти, поддерживаемые графические API и функции,
результаты бенчмарков, источник и дата данных.

Референсный минимальный класс оборудования рассчитывается на основе характеристик игры,
выбранных разрешения, качества и FPS, требований похожих игр, нормализованного класса
CPU/GPU и обязательной аппаратной совместимости.

Результат — **ориентировочная минимальная конфигурация, а не гарантия конкретного FPS**.
При недостатке данных система явно сообщает о низкой уверенности, перечисляет оговорки
и рекомендует протестировать прототип. Ложная точность исключается намеренно.

## 6. Административный раздел

Доступ по токену в заголовке `x-admin-token` (по умолчанию `admin`, меняется через
переменную окружения `ADMIN_TOKEN`). Интерфейс — экран «Администрирование».

Администратор может:

* добавлять и редактировать методы и варианты реализации;
* связывать методы с инструментами движков;
* добавлять реальные игры и источники;
* импортировать данные, включая аппаратные, из CSV и JSON;
* проверять записи и переводить их по статусам черновик → проверено → опубликовано;
* просматривать сводку наполнения и журнал целостности базы.

Публикация записи без источника запрещена.

## 9. Проверка

### Модульные и интеграционные тесты

```bash
cd backend
../.venv/Scripts/python.exe -m pytest -q
```

Покрываются: TOPSIS и его воспроизводимость, расстояние Гауэра, правила отсечения,
учёт стадии разработки, конфликты/зависимости/усиления, поиск похожих игр,
аппаратная оценка, административный раздел, сохранение проекта,
наличие источника у каждой опубликованной записи, соответствие наполнения нормам MVP.

### Сценарии раздела 8 плана

Тестами и сквозной проверкой покрыты все восемь сценариев:
3D-открытый мир, линейная 3D-игра, 2D-игра, гибридная 2.5D, мультиплеер,
большое количество NPC, ранний концепт, производство контента.

### Сквозная проверка работающего приложения

```bash
# при запущенном backend
cd backend
../.venv/Scripts/python.exe smoke_check.py --base http://127.0.0.1:8000
```

Скрипт обращается к реально работающему сервису и проверяет 83 условия:
наполнение каталога, все восемь сценариев, воспроизводимость TOPSIS,
наличие объяснений и пометок у рекомендаций, пересчёт профиля нагрузки,
поиск похожих игр, аппаратную оценку, сохранение и загрузку проекта,
закрытость административного раздела и журнал целостности базы.

Результат последнего прогона: **83 из 83 проверок пройдены**.

## 10. Экраны пользовательского интерфейса

1. Профиль игры — формат, структура мира, движок, платформы, масштаб, цели по качеству.
2. Стадия и бюджеты — стадия разработки, приоритеты, проектные бюджеты.
3. Игровые функции — что должно работать в игре.
4. Варианты реализации — подбор, ранжирование, пометки, карточка метода.
5. Риски проекта — что может стать проблемой на текущей стадии.
6. Сравнение решений — сопоставление выбранных карточек.
7. Корзина решений — выбранный набор, конфликты, зависимости, усиления.
8. Профиль нагрузки — сводное влияние набора на подсистемы.
9. Оборудование — референсный минимальный класс и оговорки.
10. Похожие игры — сверка с подтверждёнными примерами.
11. Итоговый план — отчёт по проекту.

Проект сохраняется в браузере, экспортируется в JSON и PDF, а также может быть
сохранён на сервере и восстановлен по идентификатору. Регистрация пользователей
в первой версии не требуется.

## 11. Что не входит в первую версию

Сознательно исключено, чтобы не увеличивать сложность без исследовательской пользы:

* автоматический анализ кода игры и интеграция с файлами проектов движков;
* runtime-профилирование;
* машинное обучение и LLM-рекомендации;
* автоматический сбор данных с сайтов;
* гарантированный прогноз FPS;
* пользовательские аккаунты и совместная командная работа;
* автоматическое применение оптимизаций.

Задача первой версии — доказать, что система способна формировать объяснимые,
проверяемые и зависящие от проекта рекомендации до появления критических проблем
производительности.

# Информационная система поддержки принятия решений по оптимизации разработки игр

Система помогает ещё **до появления проблем производительности** выбрать способ реализации
игровых функций, получить объяснимое ранжирование вариантов, увидеть их совместимость
друг с другом и оценить референсный минимальный класс оборудования.

Главный принцип: **каждая рекомендация объясняется, опирается на источник и зависит от
конкретного проекта**, а не выдаётся как универсальный совет.

Технический отбор партий, сравнение по функциям и новая фиксация реализованной корзины
описаны в [правилах технических рекомендаций](docs/TECHNICAL-RECOMMENDATIONS.md).
Дополнения из `proven-methods.md`, проверенные источники и исправленные утверждения — в [отчёте проверки](validation/technical-integration/proven-methods-review.md).
Основа сохраняется в текущем сеансе: последующие изменения сравниваются с ней по
трудозатратам и сложности интеграции, а требования к железу считаются по новой корзине.

Граница проекта сознательно узкая: это **локальное веб-приложение для решений
на стадии проектирования**. Оно не анализирует готовую игру, не подключается
к проекту движка, не выполняет runtime-профилирование и ничего не применяет
автоматически. Профилировщики упоминаются только как указания «чем проверить
решение», а не как встроенные инструменты.

## 1. Быстрый запуск

Требования: Python 3.11+, Node.js 18+. Установка СУБД не требуется — по умолчанию
используется локальный файл SQLite.

### Windows

```bat
start.bat
```

Скрипт создаёт виртуальное окружение, устанавливает зависимости, поднимает backend на
`http://127.0.0.1:8000` и frontend на `http://localhost:5173` в отдельных окнах консоли,
после чего открывает приложение в браузере. Окна консоли можно закрыть для остановки.

Отдельные запуски, если окружение уже подготовлено: `backend\run.bat` и `frontend\run.bat`.

### Вручную

```bash
# Backend
cd backend
python -m venv ../.venv
../.venv/Scripts/python.exe -m pip install -r requirements.txt
../.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload

# Frontend (в отдельном терминале)
cd frontend
npm install
npm run dev
```

При первом запуске backend автоматически создаёт схему и заполняет базу
демонстрационными данными (`AUTO_SEED = true`). Повторный запуск не дублирует записи.

Полезные адреса:

| Адрес | Назначение |
| --- | --- |
| `http://localhost:5173` | пользовательский интерфейс |
| `http://127.0.0.1:8000/api/health` | состояние сервиса |
| `http://127.0.0.1:8000/api/docs` | интерактивная документация API (Swagger) |

### Поддерживаемая СУБД — только SQLite

```bash
DATABASE_URL=sqlite:///./gamedev_dss.db
```

Другие схемы (`postgresql://`, …) не поддерживаются: при старте приложение
фиксирует это в журнале, `/api/health` отвечает `unavailable` с понятным
текстом ошибки, а заполнение каталога не выполняется. PostgreSQL-драйвер
в зависимости не входит.

### Миграции схемы

Схема создаётся и обновляется только миграциями Alembic — `create_all`
в старте не используется, так как он не добавляет колонки в существующие
таблицы:

```bash
cd backend
../.venv/Scripts/python.exe -m alembic upgrade head   # применить миграции
../.venv/Scripts/python.exe -m alembic check          # сверить модели со схемой
../.venv/Scripts/python.exe -m alembic revision --autogenerate -m "описание"
```

Если база была создана до появления миграций (есть таблицы, но нет таблицы
версий), старт сверяет структуру с поддерживаемой исходной схемой, ставит
штамп начальной ревизии и выполняет обычный `upgrade head`. Слепой
`stamp head` запрещён: базу с неизвестной структурой приложение не трогает,
а сообщает об отказе в журнале и `/api/health`. Перед обновлением
существующего файла рядом создаётся проверяемая резервная копия
(`<имя>.bak-ГГГГММДД-ЧЧММСС.db`). При неуспешной миграции приложение
стартует неготовым (`unavailable`), а не «как готовое», заполнение пропускается.

## 3. Модель предметной области

Основные сущности и их связи:

| Сущность | Смысл |
| --- | --- |
| `GameFunction` | игровая функция — что именно должно работать в игре |
| `Method` | вариант реализации функции или общий метод оптимизации |
| `Engine` / `EngineTool` | игровой движок и его инструменты |
| `MethodEngineLink` | связь метода с инструментом движка (8 типов) |
| `Conflict` | конфликт, зависимость или усиление между методами |
| `GameExample` | подтверждённый пример из реальной игры |
| `HardwareCPU` / `HardwareGPU` | характеристики оборудования |
| `Project` | сохранённый профиль, снимок ранжирования и голоса обратной связи |
| `ValidationIssue` | замечание проверки целостности базы |

Каждый метод и вариант реализации описан по полной схеме:

* уровень решения — **архитектура, производственный процесс, алгоритм, настройка**;
* рекомендуемый этап внедрения и стоимость позднего внедрения;
* влияние на CPU, GPU, RAM, VRAM, накопитель и сеть (шкала −3…+3);
* влияние на качество изображения и на исходную концепцию игры;
* способ расчёта — **real-time, предварительный, гибридный**;
* **алгоритм применения** — упорядоченные шаги внедрения (`application_steps`);
* **где применено** — проекты каталога с этим решением (`used_in_projects`,
  считается из примеров, отдельной таблицы нет);
* совместимость, конфликты и зависимости;
* способ последующей проверки решения.

Связь общего метода с инструментом движка имеет один из восьми типов:
прямая реализация, частичный аналог, альтернативный подход, дополнение, автоматизация,
диагностический инструмент, ограниченное применение, отсутствие встроенного аналога.
Тип `missing` — осознанный: встроенное в движок решение не считается абсолютом,
у метода всегда может быть лучшая альтернатива.

Материалы проходят состояния **черновик → проверено → опубликовано**.
В публичных рекомендациях участвуют только опубликованные записи с указанным источником —
это проверяется автоматически, в том числе тестами.

Схема не ограничивает число форматов, движков и методов: каталог расширяется через
административный раздел без изменения кода. Новый движок Трека 1 добавляется новым
файлом `seed/data/track1/<движок>.json`, новая связь — строкой в `TRACK1_ENGINE_LINKS`.

## 4. Как работает алгоритм рекомендаций

1. **Анализ проекта.** Профиль игры (формат, структура мира, стадия, движок, платформы,
   масштаб, число объектов и NPC, целевые разрешение/качество/FPS, технический API/RHI,
   накопитель, модель памяти, апскейлер, frame generation, streaming pool, draw-call budget,
   радиус симуляции, physics tick и сетевой topology, бюджеты, приоритеты).
2. **Выявление рисков.** Отдельные риски проекта на текущей стадии разработки.
3. **Отбор решений** по выбранным игровым функциям.
4. **Исключение недопустимого** — решения, нарушающие обязательные ограничения
   (формат, платформа, сложность, отсутствующие возможности движка или оборудования),
   не попадают в рекомендации, но остаются видимыми с указанием причины.
5. **Учёт стадии разработки** и стоимости позднего внедрения. Стадия повышает
   штраф за позднее внедрение и помечает решения, которые на этой стадии потребуют
   переработки готовых материалов (архитектурные — на альфе и позже): они остаются
   в расчёте и списке, но идут после решений, внедряемых напрямую, и получают
   собственную пометку с объяснением. Жёсткого календарного запрета нет: физическая
   стоимость внедрения не зависит от даты, меняется только цена переработки.
   Для каждой стадии выдаются собственные предупреждения и предложения — маршрутом
   `/api/catalog/stage-guidance` (доступен и без расчёта) и блоком `stage_guidance`
   в результате.
6. **Ранжирование методом TOPSIS** по набору критериев с весами, зависящими от
   приоритета пользователя: качество, производительность, стоимость, сбалансированный.
7. **Объяснение** — у каждой рекомендации список причин и значений критериев,
   а карточка метода дополнительно показывает шаги внедрения и проекты-применители.
8. **Связь с движком** — показывается, какой инструмент выбранного движка реализует общий
   метод, и чем его можно заменить.
9. **Предупреждения** о конфликтах и о возможном изменении концепции игры.

Пользователь добавляет решения в **корзину проекта**, после чего система пересчитывает
сводный профиль нагрузки и показывает совместимость набора. Полный перебор всех
комбинаций не выполняется — проверяется совместимость выбранного набора.

Корзина хранит **один текущий черновик**: анкету и выбранный набор. Отдельной
истории пользовательских версий намеренно нет — она выходит за границу MVP и
создавала бы второй источник истины рядом с расчётом. Сравнение «что изменил
патч» выполняется изменением набора и пересчётом: результат несёт отпечаток
входа, поэтому устаревший ответ не выдаётся за текущий.

Каждое решение помечается одной или несколькими пометками:
рекомендуется · применимо при условиях · желательно внедрить сейчас ·
позднее внедрение затруднено · требует прототипирования · может снизить качество ·
может изменить концепцию · не рекомендуется.

Каждый расчёт несёт версии алгоритма и набора данных
(`algorithm_version`, `dataset_version` в `meta`; текущие — `2.3.0` / `mvp-1.8`),
поэтому два сохранённых результата для одного профиля всегда объяснимы.

Дополнительно у каждой рекомендации есть **вилка устойчивости ранга**: места,
которые она занимает при изменении каждого веса TOPSIS на ±10% по одному.
Если вилка широкая — порядок зависит от точных весов, и это видно заранее,
а не после внедрения. При единственной альтернативе вилка не строится:
сравнивать нечего, и система честно показывает прочерк вместо псевдоточности.

## 5. Аппаратная оценка

При включённой генерации кадров пользователь может указать целевой базовый FPS
до генерации. Без него расчёт не предполагает удвоение частоты и не снижает
требования. С ним оценивается нагрузка базового рендера: стоимость генератора,
его аппаратная совместимость и достижение отображаемого FPS остаются неизвестными.
Предупреждения об оценочном бюджете draw calls и классе накопителя обозначают
риски, а не доказанные нарушения. Потребность в VRAM проверяется независимо от
наличия пользовательского лимита; альтернативы оборудования также проверяются.

Правила однократного учёта: один и тот же объём или проход считается один раз.
Бюджет подкачки (`streaming_pool_gb`) — общий объём потоковых данных, а не
расход поверх ресурсов: сверх резидентных текстур и геометрии прибавляется
только транзитная часть пула (буферы загрузки, распаковки и опережающей
подкачки), и если пул меньше резидентного набора профиля, противоречие
показывается явно. Стоимость прохода трассировки лучей масштабируется тем же
внутренним разрешением, что и остальные пиксельные стадии, и бюджетные решения
сокращают уже введённый проход. Внутреннее разрешение задаётся одним
источником — полем анкеты: карточка апскейлинга не добавляет вторую скидку, а
противоречивый ввод (апскейлинг отключён при выбранной карточке) объясняется в
допущениях. Стоимость синтеза кадров считается по полю `frame_generation` с
базовым FPS: карточка генератора не начисляет вторую стоимость, а без поля —
сообщает, что синтез не учтён.

Состав памяти и подсистем подчиняется тем же правилам. Добавочные расходы
решений в одном компоненте памяти складываются (это разные объёмы), а экономия
того же ресурса берётся один раз — по наибольшему эффекту; анимационные данные
выделены отдельным компонентом, поэтому сжатие анимаций или база движений
motion matching не меняют вершинные буферы сцены. Растровые и трассировочные
проходы выполняются на одном GPU последовательно: требование к видеокарте
считается по сумме долей бюджета кадра, а не по более лёгкой из двух частей.
Решения, чей эффект лежит вне стоимости кадра (устранение пауз компиляции,
разложение работы по кадрам, бюджет размера сборки), не получают численной
скидки: причина отсутствия вклада выводится явно, чтобы «не повлияло» не
читалось как «забыто при расчёте». Ссылка-источник карточки обязана описывать
сам механизм: источники, подобранные по названию (TAA вместо переменной
частоты затенения, обратная кинематика вместо подбора движений, DLSS вместо
нейронного сжатия текстур), заменены на профильные спецификации.

По каталогу хранятся модель и поколение, архитектура, класс производительности,
объём и пропускная способность памяти, поддерживаемые графические API и функции,
результаты бенчмарков, источник и дата данных.

Референсный минимальный класс оборудования рассчитывается на основе характеристик игры,
выбранных разрешения, качества и FPS, требований похожих игр, нормализованного класса
CPU/GPU и обязательной аппаратной совместимости.

Результат — **ориентировочная минимальная конфигурация, а не гарантия конкретного FPS**.
При недостатке данных система явно сообщает о низкой уверенности, перечисляет оговорки
и рекомендует протестировать прототип. Ложная точность исключается намеренно.

Параметры исполнения не подменяются идеальными значениями по умолчанию: `auto` и `None`
означают неизвестность. Ответ дополнительно содержит рекомендуемый класс накопителя,
грубый ориентир draw calls и `modeling_gaps` — список параметров, без которых точность
ограничена. Эти числа не являются runtime-профилированием и не обещают FPS.

Калибровка зафиксирована тестами `backend/tests/test_calibration.py`: эталонные проекты
обязаны попадать в свои классы, а относительная мощность карт в каталоге сверена
с внешним якорем (technical.city: RTX 3090 быстрее GTX 1660 Super примерно в 2.1 раза —
в каталоге 0.70/0.30). Допуск расхождения — 25%.

Методология скоринга железа (единая для всех 130 записей): `raster_score` —
PassMark G3D относительно RTX 4090 (G3D 38041 = 1.0, быстрее якоря — cap 1.0);
`rt_score` — technical.city aggregate относительно RTX 4090 (91.3 = 1.0),
0.0 — нет аппаратного RT или нет агрегата; `perf_class` — 1..5 по сетке
raster (<0.20 / 0.20–0.39 / 0.40–0.56 / 0.60–0.78 / ≥0.86) с редкими
документированными исключениями в `notes` (X3D, пограничные мобильные).
В логику идут `raster_score` / `multi_thread_score` и классы; `rt_score`
и `single_thread_score` — витринные (отображаются в карточке).

Внешние карточки реальных игр и данные Technical City используются на текущем этапе только
как вход калибровочного прогона: они помогают обнаружить неточности, пропущенные методы и
неописанные параметры. Они не являются игровыми данными продукта и не подмешиваются в
публичные рекомендации. Минимальные требования с внешнего сайта трактуются как нижний
ориентир, а не как точное соответствие заявленным в профиле разрешению, качеству и FPS.

Известное свойство (не баг): оценка консервативна относительно официальных
требований (в среднем ~+1 класс CPU). Причины: официалы часто целятся в 30 FPS
или подразумевают включённый апскейл, а инструмент считает под заявленные
60 FPS без учёта качества чужого кода. Исключения в обе стороны задокументированы
в протоколах калибровки; подгонка формул под отдельные игры запрещена —
границей служит регрессия классов выше. Процентная точность (±70% CPU/GPU)
проверяется только внешним отчётом по протоколу `docs/calibration-protocol.md`.

## 6. Административный раздел

В локальном режиме раздел открыт без токена (проверяется тестом
`test_admin_is_open_locally`). Интерфейс — экран «Администрирование»;
сводка отдаёт только числовые счётчики (`counts`) и отдельный снимок
`published`, чтобы вложенные структуры не роняли рендер.

Администратор может:

* добавлять и редактировать методы и варианты реализации, включая шаги внедрения;
* связывать методы с инструментами движков;
* добавлять реальные игры и источники;
* импортировать данные, включая аппаратные, из CSV и JSON;
* проверять записи и переводить их по статусам черновик → проверено → опубликовано;
* просматривать сводку наполнения и журнал целостности базы.

Публикация записи без источника запрещена. Черновики Трека 2 видны в сводке
наполнения, но недоступны в публичном каталоге и не влияют на рекомендации.

### Трек 1 — строго 6 движков (в публичном каталоге)

Unreal Engine, Unity, Godot, CryEngine, Source / Source 2, HeroEngine — по 20 игр
на движок в `seed/data/track1/`. Ограничение нужно, чтобы не раздувать каталог

Каждая карточка фиксирует пару «что даёт движок из коробки vs альтернатива»
и баланс по пяти осям: качество, производительность, ресурсы, стоимость
внедрения и цена опоздания, риски для концепции. Встроенное решение никогда
не считается абсолютом — это отражено типами связей (`direct … missing`)
и ранжированием TOPSIS под приоритет проекта.

Честные пометки: pre-alpha проекты не включаются как примеры (UT4 заменён
на Borderlands 3), форки и моды движков помечены в поле `engine`
(StarEngine, Titanfall/Apex-ветки Source), по HeroEngine подтверждено
только 3 shipped-релиза — остальные позиции честно помечены
прототипом или отменой.

### Трек 2 — игры-фуроры любых движков (черновики для отчёта)

71 игра в `seed/data/track2/`: 30 от Tetris до Hades (`furor.json`), топ-40 самых влиятельных по опросам и спискам (BAFTA, Polygon, Collider, EarlyGame) — от Pong до Helldivers 2 (`furor_influential.json`, все URL источников проверены через Wikipedia API, дублей с базой нет) плюс кейс модов Minecraft против GC-пиков (`gc_alloc_cases.json`, источник — независимый замер). Формула записи: что вознесло игру
в свой период (механика + техрешение + популярность). В базу попадают
со статусом «черновик», поэтому видны администратору, но исключены
из публичного каталога, TOPSIS и похожих игр. Дубли с опубликованными
примерами намеренно заменены аналогами, чтобы сидирование не понижало статусы.

## 9. Проверка

### Модульные и интеграционные тесты

```bash
cd backend
../.venv/Scripts/python.exe -m pytest -q
```

Покрываются: TOPSIS и его воспроизводимость, устойчивость ранга к дрожанию весов,
расстояние Гауэра, правила отсечения,
учёт стадии разработки, конфликты/зависимости/усиления, поиск похожих игр,
аппаратная оценка, допуск 70% на эталонных нагрузках (`test_class_regression.py`),
административный раздел (включая скалярность сводки), сохранение проекта,
обратная связь и сводка предложений, импорт анкеты из файлов движка,
генерация пресетов движков,
наличие источника у каждой опубликованной записи, соответствие наполнения нормам MVP,
публикация и переходы по статусам, обход каталога (`..` в разных кодировках),
единый формат ошибки с `request_id`, ограничение частоты запросов,
паспорт метода (шаги внедрения и проекты-применители),
невмешательство черновиков Трека 2 в публичный каталог.

Результат последнего прогона: **452 теста пройдено, 2 пропущено**.

Тесты работают с временной базой в отдельном каталоге и откатывают транзакцию после
каждого теста, поэтому не изменяют рабочий проект и не зависят от порядка выполнения.

### Тесты frontend

```bash
cd frontend
npm test          # разовый прогон
npm run test:watch
npm run typecheck # проверка типов без сборки
```

Проверяется то, что нельзя увидеть в интеграционных тестах backend:
результат расчёта всегда относится к данным на экране — после правки анкеты или
корзины прежний результат сбрасывается, а ответ на устаревший запрос отбрасывается;
порядок решений в корзине не влияет на отпечаток входа; автоматический пересчёт
запускается один раз и не повторяется после ошибки; текст ошибки backend
доходит до пользователя в разобранном виде.

Результат последнего прогона: **34 теста пройдено**, проверка типов — без ошибок.

### Непрерывная проверка

Файл `.github/workflows/ci.yml` запускает на каждое изменение ветви два задания:
backend (тесты, применение миграций на чистой базе и сверка схемы с моделями)
и frontend (проверка типов, тесты, производственная сборка). Зависимости
устанавливаются из `backend/requirements.lock` и `frontend/package-lock.json`,
поэтому состав окружения в проверке совпадает с рабочим.

### Сценарии раздела 8 плана

Тестами и сквозной проверкой покрыты все восемь сценариев:
3D-открытый мир, линейная 3D-игра, 2D-игра, гибридная 2.5D, мультиплеер,
большое количество NPC, ранний концепт, производство контента.

### Сквозная проверка работающего приложения

```bash
# при запущенном backend
cd backend
../.venv/Scripts/python.exe smoke_check.py --base http://127.0.0.1:8000
```

Скрипт обращается к реально работающему сервису и проверяет наполнение каталога,
все восемь сценариев, воспроизводимость TOPSIS,
наличие объяснений и пометок у рекомендаций, пересчёт профиля нагрузки,
аппаратную оценку, стадийные подсказки (предупреждения и предложения для каждой
стадии, закрытие уровней решений на поздних стадиях),
закрытость административного раздела и журнал целостности базы.

Результат последнего прогона: **85 из 85 проверок пройдены**.

## 10. Экраны пользовательского интерфейса

1. Профиль игры — формат, структура мира, движок, платформы (ПК Windows/Linux;
   macOS и другие цели дают инженерные объяснения, но количественный прогноз
   оборудования для них не обещается), масштаб, цели по качеству.
   Анкету можно частично собрать из файлов проекта движка (`.uproject`,
   `ProjectSettings.asset`, `ProjectVersion.txt`, URP-ассет, `project.godot`,
   `Default*.ini`): надёжно извлечённое подставляется, остальное показывается
   заметками. Код игры и сцены не читаются — это граница инструмента.
2. Стадия и бюджеты — стадия разработки с собственными предупреждениями
   и предложениями, закрытые и частично закрытые уровни решений, приоритеты,
   проектные бюджеты.
3. Игровые функции — что должно работать в игре.
4. Варианты реализации — подбор, ранжирование, пометки, карточка метода,
   вилка устойчивости ранга.
5. Риски проекта — что может стать проблемой на текущей стадии, включая
   предупреждения стадии и уровни решений, требующие переработки.
6. Сравнение решений — сопоставление выбранных карточек.
7. Корзина решений — выбранный набор, конфликты, зависимости, усиления.
8. Профиль нагрузки — сводное влияние набора: числовая шкала изменения стоимости
   кадра для CPU, GPU, RAM и VRAM; накопитель и сеть оценены качественно
   (направление и уровень влияния), потому что модели трафика и объёма данных нет.
9. Оборудование — референсный минимальный класс и оговорки.
10. Итоговый план — отчёт по проекту, пресеты движков (`DefaultScalability.ini`,
    пресет качества Unity, пресет рендеринга Godot — каждая строка знает свой
    источник) и оценки «пригодилось / не пригодилось» по решениям корзины.

Проект сохраняется в браузере в рамках сессии (анкета и корзина одного черновика).
Экспорт в JSON и PDF — через итоговый план. Регистрация пользователей
в первой версии не требуется.

## 11. Что не входит в первую версию

Сознательно исключено, чтобы не увеличивать сложность без исследовательской пользы:

* автоматический анализ кода игры и сцен (читаются только файлы настроек
  проекта — движок, версия, название, разрешение, заметки о рендере);
* runtime-профилирование и подключение к запущенной игре;
* машинное обучение и LLM-рекомендации (обратная связь только предлагает
  правки достоверности с указанием голосов — применяет их человек);
* автоматический сбор данных с сайтов;
* гарантированный прогноз FPS;
* пользовательские аккаунты и совместная командная работа;
* автоматическое применение оптимизаций (пресеты — это файлы для копирования
  в проект, а не запись в него);
* различие топологий сессий: анкета знает только факт мультиплеера и число
  игроков, но не различает выделенный сервер и P2P. Налог хоста (FPS, читы,
  отсутствие арбитра — кейс Helldivers 2, `CALIBRATION_WILD.md`) отдельным
  риском не выделяется; сетевые методы при P2P выдаются как условные.

Система работает с проектными данными, которые вводит пользователь,
а не с готовой игрой: проверять решения предлагается профилировщиками
движков вручную, по указанной в карточке методике. Это граница проекта,
а не недоработка, — инструмент поддержки решений на стадии проектирования,
а не анализатор собранного билда.

Задача первой версии — доказать, что система способна формировать объяснимые,
проверяемые и зависящие от проекта рекомендации до появления критических проблем
производительности.

### Направления дальнейшего развития

Расширение каталога не требует изменения кода (новые файлы `track1/`,
строки `TRACK1_ENGINE_LINKS`), поэтому в коде остаются только точечные заделы:

* сквозной сценарий Playwright на весь визард — логика экранов уже покрыта тестами
  состояния, браузерный прогон даёт дополнительную уверенность в разметке;
* генерация типов frontend из OpenAPI вместо их ручного дублирования в `types.ts`;
* property-based тесты (Hypothesis) для границ допустимых значений и воспроизводимости
  поверх существующих проверок диапазонов;
* отображение шагов внедрения и проектов-применителей в карточке метода
  интерфейса (API уже отдаёт `application_steps` и `used_in_projects`).

## Главное: моя вчерашняя гипотеза «нет исторического слоя» неверна

Владелец проекта поправил: задача модели — определить, какой ПК хватит **сегодня**, чтобы запустить игру. Ретро-игра с простой графикой и сейчас должна требовать мало. Оптимизация лишь рационально распределяет нагрузку; если игра изначально лёгкая, модель обязана это показать. Исследование это подтверждает: причина расхождений не в годе выпуска, а в конкретных дефектах кода и данных.

## Реализовано: пункт 1 разд. 9.1 (Windows/Linux)

Новый модуль `backend/app/services/targets.py`:
- `OS_NATIVE_APIS`: DirectX (9/11/12) — только Windows; Vulkan/OpenGL — обе ОС.
- `OS_DEFAULT_API`: `auto` разрешается отдельно по цели (Windows → dx12, Linux → vulkan).
- `ENGINE_APIS` — объявленные наборы API движка по ОС; пустое множество = «не заявляется».
- `resolve_targets()` → список `PlatformTarget` (platform, api, api_source, compatible, engine_check, notes).
- Несовместимость ОС↔API блокирует подбор оборудования и называется по имени цели;
  расхождение движок↔API — **только предупреждение** (зависит от версии, measurement нет).

Metal удалён из `RenderAPI` (enums, `_API_FACTORS`, `_gpu_feature_support`).

`hardware.py`:
- `_target_models()` / `_target_evaluations()` / `_target_rows_out()` — модель считается
  отдельно по каждой совместимой PC-цели; общий ориентир = максимум по целям
  (удовлетворяет обеим, а не среднее). Связывающая цель (binding) даёт разбор подсистем.
  Используется в `estimate_hardware`, `_load_indices` и `build_contributions` — расхождение
  экранов невозможно.
- Нет ни одной совместимой цели → `reference_* = None`, `unmet` с явным сообщением,
  но числа (индексы, память) сохраняются.
- Вывод `HardwareEstimateOut.targets` (схема `PlatformTargetOut`), фронтенд показывает
  обе цели в `HardwareScreen`.

Резерв окружения (разд. 3.3):
- `OS_RAM_RESERVE_GB = 3.0` (заменил 2.5), `BACKGROUND_RAM_RESERVE_GB = 1.0` — отдельный
  компонент `background` в составе памяти, `OS_VRAM_RESERVE_GB = 0.5` (одинаков для
  dedicated и unified: меньший резерв на UMA был бы необоснованной скидкой).
- `CPU_HEADROOM_SHARE = 0.10`, `GPU_HEADROOM_SHARE = 0.05` — через `_cpu_need()` /
  `_gpu_need()`, один раз при проверке кандидата (`_pick_cpu`, `_pick_gpu`, альтернативы).
- Оговорка о необмеренном характере резерва — в `assumptions` и `caveats`.

**Найден дефект модели:** рекомендации почти не зависят от профиля — в топ-10 по всем 58
играм встречается лишь 13 разных методов из 111, 7 из них попадают в десятку у всех игр,
средняя Жаккард-похожесть десяток 0.86. Причина — равенство экспертных баллов при
`stage=release` + TOPSIS: верх списка формируется обходом каталога, а не профилем.
Корзины реальных решений при этом используют 73 разных метода. Сравнивать игры по
рекомендациям нельзя до исправления ранжирования.

Подводящие камни, встретившиеся при разборе партий:
- `AnvilNext` содержит подстроку «Unity» — движок определять по `anvil` первым;
- «UE5 для Orion» / «не UE5» в описаниях ломают поиск `ue[345]` — искать только «unreal engine N»;
- паспортный кадровый бюджет и строка Targets в партиях противоречат друг другу
  (HL2: «33.3 мс (60 fps цель)») — приоритет отдан кадровому бюджету;
- `EngineTool` связан через `engine_id`, `Method` — через `function_id` (не `engine_code`/`function_code`).

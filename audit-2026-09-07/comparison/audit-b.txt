# Глубокий аудит `game-inspect`: что мешает цели «~70% точности по железу»

## Контекст цели

**Заявленная цель** (по `README` §4, §5, §11 и `docs/calibration-protocol.md`): выдавать ориентировочный класс оборудования с долей попаданий в **±1 класс ≥70%** на внешнем наборе из 66/200 игр (дикая калибровка), плюс выдавать пользователю плюсы/минусы решений и список того, что проект сознательно не может учесть (его ограничения по дизайну).

**Текущая фактическая позиция** (выводы из 3 параллельных глубоких аудитов):
- В коде есть **20+ дефектов в `hardware.py`**, каждый из которых сдвигает класс на 30–100% (то есть ±1–2 класса)
- В seed-данных **26+ кодов в `optimizations_used` не существуют в каталоге методов** → `matching_optimizations` и `used_in_projects` мертвы для базовых примеров
- В seed-данных **платформы** записаны как `PS4/PC/Xbox One/Mobile` (человекочитаемые), а не как enum-значения `pc_windows/ps4/...` → Гауэр не матчит профиль с примером
- CI **не прогоняет** `wild66/wild200` и `smoke_check.py` — целевой порог 70% не верифицируется автоматически
- README **обещает** отображать `application_steps` и `used_in_projects` в UI, но фронтенд их не рендерит
- `test_tolerance_70.py` — это **8 точечных** ручных кейсов, а не реальный прогон 66/200. Цифра `90.2%` существует только в комментарии

## А. БЛОКЕРЫ ЦЕЛИ (мешают достичь 70%)

### A1. `RT` не повышает `gpu_index` — критический сдвиг класса
**Файл:** `backend/app/services/hardware.py:278-281, 307`
```python
gpu_index = GPU_CALIBRATION * res * render_fps * quality * content * feature_gpu * gpu_method
            * api_gpu * _UPSCALER_GPU_FACTOR.get(upscaler, 1.0)
# required_rt вычисляется на строке 307, но в gpu_index не входит
```
RT-проект (Cyberpunk/Cyber RT, Control) в 4K замедляет рендер в 2–4×. Здесь этого множителя нет. **Результат: класс железа для RT-проекта занижается на 1–2 класса, промахи в ±1 класс становятся промахами в ±2–3.**

**Фикс:** `if required_rt: gpu_index *= 1.5` (или зависящий от разрешения множитель 1.3 в 1080p, 2.0 в 4K).

### A2. Апскейлер при `upscaling_method="auto"` не даёт скидки в 4K
**Файл:** `hardware.py:275-280`
```python
upscaler = profile.upscaling_method
if upscaler == "auto" and "temporal_upscaling" in method_codes:
    upscaler = "taa"
gpu_index = ... * _UPSCALER_GPU_FACTOR.get(upscaler, 1.0)
```
Для профиля `2160p/high + upscaling_method=auto + корзина без temporal_upscaling` → `upscaler="auto"`, фактор 1.0. То есть 4K-нативный рендер считается как 1080p. При этом сам же код в `_modeling_gaps:218-219` сообщает: «Не указан upscaler: итоговая GPU-нагрузка для высокого разрешения может отличаться» — **знает про проблему, но не чинит**.

**Фикс:** для `target_resolution ∈ {1440p,1600p,2160p,4k}` без явного upscaler: `gpu_index *= 1.3–1.6` (повышающий множитель за нативный рендер).

### A3. `frame_generation=True` без `base_render_fps` ложно завышает требования
**Файл:** `hardware.py:139-143, 282-285`
```python
def _render_fps_factor(profile):
    if profile.frame_generation and profile.base_render_fps is not None:
        return _fps_factor(profile.base_render_fps)
    return _fps_factor(profile.target_fps)  # ← фоллбэк: 144 FPS как настоящие
```
При `target_fps=144, frame_generation=True, base_render_fps=null` — формула считает 144 нативных FPS, а пользователь получит 60 базовых × 2 генерации. **Завышение класса CPU/GPU на 60–150%.** `_modeling_gaps:222-225` это признаёт, но не компенсирует.

**Фикс:** если `frame_generation=True and base_render_fps is None`, использовать `target_fps * 0.55` или фиксированно 60.

### A4. `cpu_index` не использует `render_fps_factor`
**Файл:** `hardware.py:282-285`
```python
cpu_index = CPU_CALIBRATION * content * feature_cpu * cpu_method * (0.6 + 0.4 * fps)
            * api_cpu * storage_cpu
# ↑ использует обычный _fps_factor(target_fps), не _render_fps_factor
```
При включённой FG физическая нагрузка CPU определяется `base_render_fps`, а не `target_fps`. **+20–50% к cpu_index при FG.**

**Фикс:** `... * (0.6 + 0.4 * render_fps)` (использовать `render_fps`).

### A5. `vram_limit_gb` принимается, но не фильтрует GPU
**Файл:** `hardware.py:342-368` (особенно 344, 358)
```python
def _pick_gpu(pool, index, *, required_rt, vram_limit_gb, vram_gb):
    if required_rt: pool = [g for g in pool if _supports_ray_tracing(g)]
    pool = [g for g in pool if g.vram_gb >= vram_gb]  # ← фильтр по потребности
    candidates = [g for g in pool if g.raster_score >= index]
    # vram_limit_gb не используется!
```
Пользовательский лимит проверяется **только потом** в `_pick_references:401` как пометка `unmet`. Карта с 12 ГБ пройдёт в референс при `vram_limit_gb=4`, а пользователь увидит «превышено» в caveats. **Это нарушает заявленное поведение** («пределы памяти — обязательные ограничения») и даёт рекомендацию, заведомо превышающую бюджет.

**Фикс:** добавить `if vram_limit_gb is not None: pool = [g for g in pool if g.vram_gb <= vram_limit_gb]`.

### A6. `feature_gpu`/`feature_cpu` без верхнего cap
**Файл:** `hardware.py:249-250, 266-271`
```python
feature_gpu = 1.0 + sum(FEATURE_GPU_LOAD.get(f, 0.05) for f in profile.functions)
# нет cap. Для 20 функций feature_gpu ≈ 1.0 + 20*0.10 = 3.0+
```
`gpu_method` имеет cap `[0.45, 2.0]`, но `feature_gpu` — нет. Корзина из 20 функций даёт ложное «exceeds» для нормальных проектов. **Ложно-положительные промахи вверх.**

**Фикс:** `feature_gpu = min(feature_gpu, 2.0)`, аналогично для CPU.

### A7. VRAM линейна от разрешения, без учёта RT и текстур-HD
**Файл:** `hardware.py:288`
```python
vram_gb = 1.4 + 2.0 * res + 2.4 * (quality - 0.7) + 1.2 * (content - 1.0)
# res=3.0 (4K) → +6 ГБ линейно. Реально 4K с RT BVH = ещё +1-2 ГБ.
```
RT-текстуры и BVH жрут 1–4 ГБ дополнительно. Здесь никак не моделируется. **4K+RT проект получит заниженный VRAM, рекомендация может быть картой с 6 ГБ, когда реально нужно 10+.**

**Фикс:** если `required_rt`, добавить `+1.5` или `+ res * 0.5`.

### A8. `wild66/wild200` нигде не прогоняются в CI
**Файл:** `.github/workflows/ci.yml` (68 строк, полностью прочитан)
```yaml
- python -m pytest -q
- alembic upgrade head && alembic check
```
**Ни `smoke_check.py`, ни `wild66.json`, ни `wild200.json` в CI не запускаются.** Заявленная цель 70% не верифицируется автоматически. `test_tolerance_70.py:1-13` обещает «46/51=90.2%» в шапке, но:
- Прогоняет только 8 ручных кейсов
- Метрика «±1 класс по CPU и GPU одновременно» не вычисляется, проверяется только `_within_one` по каждой оси отдельно
- `wild66.json` импортируется только в комментарии, файл лежит в корне проекта

**Фикс:** добавить job в CI, который:
1. Поднимает backend с свежей БД
2. Гоняет каждый сценарий из `wild66.json` через `POST /api/hardware-estimate` + `POST /api/recommend`
3. Сравнивает полученный класс с эталоном
4. Падает, если доля попаданий в ±1 класс < 70%
5. Исключения (сценарии без полного эталона) выводятся отдельно, не «выкидываются молча»

### A9. Seed `optimizations_used` содержит коды, не существующие в `methods_data`
**Файл:** `backend/app/seed/data/game_examples.json:28-34, 70-74, 111-115, 151-156, 195+`
```json
"optimizations_used": ["gpu_procedural_placement", "gpu_instancing", "lod_hierarchy",
                        "level_streaming", "texture_streaming"]
```
Подтверждено: в `methods_data.py` нет ни `gpu_instancing`, ни `lod_hierarchy`, ни `level_streaming`, ни `texture_streaming`, ни `animation_lod`, ни `object_pooling`, ни `occlusion_culling`, ни `mesh_compression`, ни `gpu_culling`, ни `deferred_rendering`, ни `dynamic_resolution`, ни `instanced_rendering`. Реальные коды: `gpu_instancing_vegetation`, `hierarchical_lod`, `world_partition_streaming`, `virtual_texturing` и т.д. **Эти коды никогда не совпадут с `basket_methods.code`** → `matching_optimizations` пуст, `used_in_projects` для базовых методов пуст, **карточка метода теряет социальное доказательство**.

Также в `track1/*.json` (20 игр на 6 движков) — 120 записей, и большинство использует те же невалидные коды.

**Фикс:** построить маппинг `legacy_code → method_code` (например, `gpu_instancing → gpu_instancing_vegetation`, `lod_hierarchy → hierarchical_lod`, `level_streaming → world_partition_streaming`) и применить при seed, плюс написать тест `test_example_optimizations_resolve_to_methods`.

### A10. Seed `platforms` использует строки вне enum
**Файл:** `backend/app/seed/data/game_examples.json:10-13, 50-54, 91-96, 132-136, 173-180`
```json
"platforms": ["PS4", "PS5", "PC", "Xbox One", "Xbox Series X|S", "Switch", "Mobile"]
```
Backend `Platform` enum (по `models/enums.py` и тестам `test_profile_influence.py:81-85`): `pc_windows`, `pc_linux`, `macos`, `android`, `ios`, `ps4`, `ps5`, `xbox_one`, `xbox_series`, `switch`. **Ни одно значение в seed не матчится напрямую** (даже `"PC"` vs `"pc_windows"`). Гауэр считает `pc_windows` vs `PS4` как 100% различие → similarity падает → похожие игры всегда «далеки» от профиля пользователя.

**Фикс:** нормализовать platforms в seed при загрузке (lowercase + map: `PC → pc_windows`, `PS4 → ps4`, `Xbox One → xbox_one`, `Switch → switch`, `Mobile → android` или удалить).

### A11. `test_tolerance_70.py` — overfit, а не валидация
**Файл:** `backend/tests/test_tolerance_70.py:1-125`
- 8 ручных кейсов, все `1080p/60/high, linear/hub`, без RT, без апскейла, без 4K, без open-world heavy
- Шапка обещает «90.2%», но это число — ручной подсчёт, не автопрогон
- Если кто-то «подкрутит» формулу под эти 8 кейсов, общая точность может упасть до 0%
- Нет параметризации, нет wildcard-ов, нет воспроизводимости

**Фикс:** параметризовать по `wild66.json` с матрицей режимов `720p/low/30` … `4k/ultra/60` из `calibration-protocol.md:31-34`, исключения логировать, а не игнорировать.

## B. ДЕФЕКТЫ КАЧЕСТВА (напрямую не блокируют 70%, но деградируют)

### B1. `input_fingerprint` не сортирует `profile.functions`
**Файл:** `backend/app/schemas/catalog.py:616-618` + `frontend/src/store.tsx:86-88`
```python
payload_dict = {
    "profile": profile.model_dump(mode="json"),  # ← список functions сохраняет порядок
    "basket": sorted(basket or []),              # ← корзина сортируется
}
```
Backend сортирует `basket`, но не `profile.functions`. Frontend (`stableStringify` в `store.tsx:86`) тоже не сортирует `profile.functions`. **Последствие:** пользователь переставил галочки функций → `input_key` изменился → фронт сбрасывает результат как «устаревший» (`resultStale=true`, `store.tsx:297`), хотя данные по сути те же. Лишний пересчёт, потенциальный ложный stale.

**Фикс:** `profile.model_dump(mode="json", include={"functions": sorted(...)})` или сортировать явно после `model_dump`.

### B2. `audio_complexity="unknown"` вызывает `KeyError` 500
**Файл:** `backend/app/schemas/catalog.py:85` + `hardware.py:258-259`
```python
if profile.audio_complexity:
    feature_cpu += _AUDIO_CPU_LOAD[profile.audio_complexity]  # KeyError если "unknown"
```
Схема `LevelValue | None` включает `"unknown"`. Код без fallback. **Фронт-баг:** пользователь выбирает «не указан» в аудио → backend падает с 500.

**Фикс:** `_AUDIO_CPU_LOAD.get(profile.audio_complexity, 0.0)`.

### B3. `_consistent_counts` мутирует `object_count_level` — расхождение input_key
**Файл:** `backend/app/schemas/catalog.py:128-145`
```python
@model_validator(mode="after")
def _consistent_counts(self):
    if self.object_count is not None:
        derived = self._level_from_count(self.object_count, ...)
        if derived != self.object_count_level:

```
Если пользователь задал `object_count=5000, object_count_level="low"`, валидатор перезаписывает на `"medium"`. `model_dump()` возвращает изменённый уровень → backend `input_fingerprint` отличается от того, что frontend «думал» отправил → `inputKey` расходится → ложный stale.

**Фикс:** хранить пользовательский `object_count_level` отдельно от derived, использовать derived только в `recommender/hardware`.

### B4. `upscaling_method="taa"` в `_UPSCALER_GPU_FACTOR` — некорректная экономия
**Файл:** `hardware.py:64-67`
```python
_UPSCALER_GPU_FACTOR = {"auto": 1.00, "none": 1.00, "taa": 0.96,
                         "fsr": 0.84, "dlss": 0.80, "xess": 0.86}
```
TAA — это антиалиасинг, не апскейлер. 4% экономии — фикция. `temporal_upscaling` (метод в корзине) + `upscaling_method="auto"` → `upscaler="taa"` → ложная скидка.

**Фикс:** поднять `taa` до 1.00 или убрать TAA из upscaler-факторов (он не должен стоять рядом с DLSS).

### B5. Frontend `RESOLUTIONS` отдаёт `2160p`, тесты ожидают `4k`

const RESOLUTIONS = [

В backend `Resolution` enum — **оба** `2160p` и `4k` (RESOLUTION_FACTOR одинаков 3.0, но значения строк разные). В `test_calibration.py:159` используется `target_resolution="4k"`. **Пользовательский выбор `2160p` не сматчится с калибровочными якорями по `4k`**, если такие тесты расширятся.

**Фикс:** в UI давать `"4k"`, или в тестах использовать `"2160p"`, или ввести алиас в схеме.

### B8. Двойной учёт `confidence` в TOPSIS
**Файл:** `backend/app/services/recommender.py:412, 421`
```python
risk = (complexity - 1) / 4.0 * 0.6 + (1 - confidence) * 0.4  # cost-критерий
# и отдельно:
matrix_row.append((criterion_confidence, method.confidence))  # benefit-критерий
```
`confidence` влияет дважды: в `risk` (как «неуверенность») и в отдельном критерии. **Искажает TOPSIS-ранжирование в пользу высоко-confidence методов, даже если они хуже по другим критериям.**

**Фикс:** убрать `(1 - confidence)` из risk и оставить только `complexity`-компоненту.

### B9. `quality_preservation` инвертирована по смыслу
**Файл:** `recommender.py:415`
```python
quality_preservation = (method.quality_impact + 2) / 4.0
# quality_impact=+2 → 1.0 (максимум), quality_impact=-2 → 0.0
```
Критерий назван «сохранение качества», но `quality_impact=+2` означает «метод улучшает качество», а не «сохраняет». Метод с `quality_impact=+2` (например, ray tracing, дающий лучшее освещение) получает максимум, хотя он не «сохраняет» — он улучшает.

**Фикс:** переименовать в `quality_improvement` или сделать `(-quality_impact + 2) / 4.0`.

### B10. `aggregate_load` clamp теряет совокупный эффект корзины
**Файл:** `recommender.py:786-796`
```python
# raw = sum(impact_*) ∈ [-6..+6]; 50 + raw * (50/6) → clamp [0..100]
```
Для корзины из 10 методов `raw = -30..+30` → clamp. **10 оптимизаций дают «не влияет» (50)**, потому что сумма ушла в clamp. Совокупный эффект скрыт.

**Фикс:** делить на количество методов или использовать sigmoid.

### B11. `audio_complexity` — нет GPU-вклада для spatial audio
**Файл:** `hardware.py:39-50, 68` — `_AUDIO_CPU_LOAD` есть, но в `FEATURE_GPU_LOAD` нет. Spatial audio + HRTF convolution reverb нагружает GPU. **Микро-дефект, не критично.**

### B12. `H14` в апдейт: RT-несовместимая карта показывается как «ориентир»
**Файл:** `hardware.py:453` (проверено)
```python
reference_gpu = max(compatible_gpus, key=lambda g: g.raster_score) if compatible_gpus else None
```
При `rt_missing=True` `compatible_gpus` уже отфильтрованы по API, но **не по RT** (фильтр RT идёт в `_pick_gpu`, не здесь). Показываемая карта может не иметь RT, а пользователю уже сказали «RT обязателен» в caveats. Противоречие.

**Фикс:** при `rt_missing` либо не показывать референс, либо явно пометить «наиболее производительная карта без RT в каталоге».

### B13. CPU выбирается только по `multi_thread_score`, не по `single_thread`
**Файл:** `hardware.py:371-377`
```python
def _pick_cpu(pool, index):
    candidates = [c for c in pool if c.multi_thread_score >= index]
```
Для старых однопоточных проектов (Doom, GTA III, HL2) ST важнее MT. Это и есть «консервативна +1 класс CPU» из README, выданная за свойство, а не баг. **Систематическое завышение CPU-требований для ST-bound игр.**

**Фикс:** для проектов с `world_type ∈ {linear, hub, arena}` и `multiplayer=False` использовать `max(ST_need, MT_need)`.

### B14. `gower.find_similar` без порога similarity
**Файл:** `backend/app/services/gower.py:178`

## C. ОГРАНИЧЕНИЯ ПО ДИЗАЙНУ (не дефекты, но пробелы — что проект не умеет по архитектуре)

Эти вещи `README` явно выводит из scope, и пользователь должен это понимать. Система должна честно сообщать о них в `_modeling_gaps` или в плане.

1. **Нет runtime-профилирования** — формула не может измерить реальные draw calls, реальную VRAM-пиковую нагрузку, реальный frame time. Только «оценка по анкете».
2. **Нет ML/LLM** — все коэффициенты экспертные (`FEATURE_GPU_LOAD`, `WEIGHT_PROFILES`, `GPU_CALIBRATION`).
3. **Анкета не различает P2P / dedicated / lockstep** для налога хоста. README §11 упоминает это. В коде есть `network_topology`, но `_modeling_gaps` пишет только «P2P/dedicated/lockstep имеют разную цену» — без численных множителей.
4. **Движок не влияет на индекс** напрямую (только через `engine_support` в корзине). Для `Fox Engine` vs `Source Engine` с теми же функциями — одинаковый индекс, что неверно.
5. **Анкета не различает уровни освещения** (только `baked_lighting` как функцию). Нет поля «количество динамических источников света», нет «shadow resolution», нет «RT-уровень».
6. **Нет поля «целевой размер билда»** в ГБ, кроме `size_limit_gb`. Реально размер билда и размер install — разные.
7. **Нет поля «целевая плотность трафика/аудитории»** для серверных сценариев.
8. **Сетевая топология не влияет на `cpu_index` через моделирование трафика**, только через `_STREAMING_METHODS` и `network_topology +0.04/+0.08`.

## F. КРИТИЧЕСКИЕ ОТВЕТЫ НА ВОПРОСЫ

**Q: Возможно ли 70% с текущей формулой?**
A: Нет. Без фиксов A1–A7 (7 правок в `hardware.py`) формула систематически сдвигает класс на ±1–2 для RT/4K/FG сценариев, а это критическая масса кейсов в `wild66/wild200`.

**Q: Какие плюсы/минусы связаны с архитектурными решениями?**
A: Архитектура — **главный плюс**: многослойная защита от черновиков (repositories, repositories.methods_by_codes, draft→reviewed→published, alembic миграции с integrity constraints, test_publication 18 тестов). Минусы архитектуры:
- **Двойная бухгалтерия доверия** — `confidence` влияет и в risk, и в отдельный критерий (B8)
- **Экспертные веса без калибровки** — `WEIGHT_PROFILES`, `FEATURE_GPU_LOAD/CPU_LOAD` не обоснованы
- **Локальное приложение без runtime-профилирования** — анкета не может измерить реальное
- **TOPSIS на векторной норме чувствителен к масштабу** — `quality_preservation ∈ [0..1]`, `concept_fidelity ∈ [0..2]` имеют разные шкалы

**Q: Что проект не умеет по дизайну?**
A: См. C1–C8. Ключевое: не различает P2P/dedicated/lockstep по стоимости хоста, не моделирует движок напрямую, не учитывает плотность света/растительности, GC-пики, shader complexity, fill-rate, HD-pack, DLSS-режимы, thermal limit. **Эти пробелы должны быть явно в `_modeling_gaps`/`README`, а не «не упомянуты».**

## G. ИТОГ

Проект имеет **сильный фундамент** (тесты публикации, защита от черновиков, статусы, миграции, чувствительность, репродуцируемость), но **достижению 70% мешают**:

1. **11 блокеров** (A1–A11) — каждый даёт ±1 класс
2. **~44 дефекта качества** (B1–B44) — копят ошибку
3. **8 пробелов дизайна** (C1–C8) — должны быть явно в gaps

Минимальный фикс для 70%: **A1–A11 + B1 + B2 + B7 + A9 + A10 + A11/A8** = 15 правок. Это реалистично за 2–3 недели.

После фикса ядра: 70% в ±1 класс достижимо, потому что классы широкие по построению (`0.20/0.39/0.56/0.78/0.86`).

Для перехода к «30% погрешности по производительности» (а не «в ±1 класс») — нужно добавить анкетные поля из `B44` и пересмотреть `GPU_CALIBRATION/CPU_CALIBRATION` по `wild200.json` с матрицей режимов. Это **отдельный этап на 2–4 месяца**.

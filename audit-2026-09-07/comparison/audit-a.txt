# Глубокий аудит `game-inspect`: почему цель «~70% точности железа» сейчас недостижима

> Терминология: у вас в запросе «70% погрешность в производительности», в `docs/calibration-protocol.md:21-25` — «доля попаданий в ±1 класс, цель ≥70%», в `backend/tests/test_tolerance_70.py:1-7` — «46/51=90.2%». Это **три разные метрики**. Подмена — корень половины проблем ниже.

## 1. Метрика 70% — главная несостыковка

### 1.1. ±1 класс != ±30% производительности
Классов всего 5. Сетка из `README.md:270-272`:

```
<0.20 / 0.20-0.39 / 0.40-0.56 / 0.60-0.78 / ≥0.86
```

Ширина класса ~0.15-0.20 по `raster_score`. Это ~1.7-2.0x по реальной производительности. Допуск ±1 класс = **допуск в 3-4x по FPS/растру считается «успехом»**.

Это не «70% точность», это «70% попаданий в очень широкие ворота». Пользователь ждет «угадали perf с ошибкой ~30%», система меряет «угадали ворота шириной 200%».

Плюс дыры в сетке: `0.56-0.60`, `0.78-0.86` не принадлежат ни одному классу. `perf_class` в `backend/app/seed/data/hardware.json` задается **вручную**, а не вычисляется из `raster_score`. Инверсии возможны и ничем не ловятся, кроме теста 3 карт.

### 1.2. Метрика заявлена, но не исполняется кодом
- `wild66.json`, `wild200.json` лежат в корне, в продукт не импортируются. Это правильно по `calibration-protocol.md:5-8`, но:
- цифра `46/51=90.2%` существует только в комментарии `test_tolerance_70.py:7`. Автопрогона `wild66.json -> /api/hardware-estimate -> метрика` нет.
- `test_tolerance_70.py:43-124` проверяет **8 точечных кейсов**, все `1080p/60/high, linear/hub`, все без RT, без апскейла, без 4K, без open-world heavy. Сломаете формулу для `1440p+RT+DLSS` — тесты пройдут.
- `test_calibration.py:143-166` фиксирует 3 синтетических якоря (`0.05-0.20`, `0.15-0.35`, `0.55-0.90`). Это не внешние игры.

Итог: порог 70% можно тихо потерять, CI не заметит.

### 1.3. Запрещенная подгонка уже в коде
`backend/app/services/hardware.py:87-98`:

```python
GPU_CALIBRATION = 0.20 # поднят с 0.18 ...
CPU_CALIBRATION = 0.25 # снижен с 0.26 ...
```

Комментарий честно говорит: подкрутили чтобы `GTA/Cyberpunk` сошлись и `2D-игра` не требовала `i7-8700K`. А `README.md:286-287` и `calibration-protocol.md:43-45` запрещают «подгонку формул под отдельные игры». Собственное правило нарушено. Это overfit под 2-3 кейса.

## 2. Ядро `hardware.py` — линейная свертка, не модель perf

`_load_indices()` `hardware.py:230-312`:

```
gpu_index = 0.20 * res * render_fps * quality * content * feature_gpu * gpu_method * api * upscaler
cpu_index = 0.25 * content * feature_cpu * cpu_method * (0.6+0.4*fps) * api * storage
```

Дефекты:

1. **Все мультипликативно и независимо.** `RT + 4K + ultra` перемножаются, в реальности суперлинейно (BW + RT + fill-rate). Взаимодействий нет.
2. **Движок не влияет на индекс.** `unreal/custom/source` различаются только в `engine_support`, не в нагрузке. Проект на `Fox Engine` с half-res diffuse из вашего PDF и проект на `Creation Engine 2` с говенным CPU-стримингом получат одинаковый индекс при одинаковых функциях. Это прямо противоречит реестру, где половина карточек — про движок.
3. **Веса `FEATURE_GPU/CPU_LOAD:27-51` — экспертные константы.** `dynamic_global_illumination:0.28`, `split_screen:0.20` — ни регрессии, ни доверительных интервалов, ни источника на каждое число. В PDF у каждого `+/-` есть источник, здесь — нет.
4. **API факторы `_API_FACTORS:53-61` — магия:** `dx9:(0.92,1.15)`, `dx12:(1.02,0.94)`. Откуда 15% CPU-штраф DX9? Из кейса GTA IV? Если да — это обобщение одного кейса `GTA IV DX9 draw calls` на все игры. Неверно для 2D.
5. **Апскейл `_UPSCALER_GPU_FACTOR:64-67`:** `dlss:0.80, fsr:0.84` — один множитель на все разрешения и режимы Quality/Performance. DLSS Performance в 4K дает ~2x, DLSS Quality в 1080p ~1.2x. Ошибка до 60%.
6. **VRAM `288-291`:** `1.4+2.0*res+2.4*(quality-0.7)+...` — нет RT, нет текстур, нет HD-pack. Кейс `Far Cry 6 HD Texture 11-12GB` из PDF формула не воспроизведет: при `1440p/high` даст ~6-7GB всегда.
7. **RAM `292-297`:** `4.0+4.0*content+2.0*object_effective` где `object_effective 0..1`. Разница между `100` и `1_000_000` объектов — **2GB**. `test_profile_influence.py:42-61` проверяет только `>`, не величину. Чувствительность символическая.
8. **`_fps_factor:129-136`:** кусочно-линейная `0.62@30 -> 1.7@144`. CPU-bound при 120+ не моделируется, только `caveat` строкой `hardware.py:542-546`. Индекс растет, а надо бы насыщаться по GPU и взлетать по CPU.
9. **Frame Generation `139-143,164-170`:** без `base_render_fps` индекс не меняется. Это честно, но UX-ловушка: пользователь включил FG, ждет снижения требований, получает то же число + `modeling_gaps`. Тест `test_frame_generation_does_not_invent_base_fps` фиксирует это как фичу.
10. **Draw calls `164-177`:** `500+24000*content [+4000*npc] *0.65 если LOD`. Потолок ~55k. Бюджет `draw_call_budget` до `1_000_000` (`schemas/catalog.py:82`) никогда не превысится. Проверка мертва для больших значений.
11. **`simulation_radius:261,283`:** `1+min(0.25, radius/40000)`. При 10км уже насыщение. Для `64км² Сталкер 2` и `San Andreas` разницы нет.
12. **`physics_tick:263-264`:** влияет только если выбрана `physics_simulation`. `destruction_simulation`, `crowd_simulation` игнорируются. Тик 66.6 Гц из `Half-Life 2` карточки посчитается, тик толпы — нет.

### Выбор референса `_pick_gpu/_pick_cpu:336-371`

- Сначала фильтр `vram_gb >= vram_gb`, потом `raster_score >= index`, потом `min(class, score)`. Если VRAM формула завысила на 1GB — правильная карта отбрасывается, возвращается `max(... )` как «ориентир» с `exceeds=True`, но `gpu_class` все равно = класс этой max-карты. UI покажет «класс 5» как рекомендацию, хотя это флаг провала.
- `rt_score` витринный, в выборе не участвует, только binary-фильтр `_supports_ray_tracing:101-104` по подстроке `ray tracing/rtx/rt core`. Опечатка в `hw_features` = потеря всех RT-карт.
- CPU выбор только по `multi_thread_score`. `single_thread_score` витринный (`README:273-274`). Для старых игр реестра (`Doom`, `GTA III`, `HL2`) важен ST. Оценка будет систематически завышать CPU для однопоточных проектов — это и есть «консервативна +1 класс CPU» из `README:282-285`, выданная за свойство, а не баг.
- Мобильный фильтр `_MOBILE_GPU_MARKERS:320-323` по подстроке: `vega`, `(tm)`, `780m`. Любая десктопная `Vega 64` улетит в мобильные. CPU фильтр `_MOBILE_CPU_RE=h$|van gogh` — `i7-8700H`? Нет, `h$` ловит только концевую `h`, но `Ryzen 7 7840H`? Да. Хрупко.

## 3. Данные каталога загрязняют оценку

1. **HeroEngine:** `README:360-364` честно: «подтверждено только 3 shipped, остальные прототип/отмена», но все 20 лежат в `seed/data/track1/` со статусом `published` (`seeder.py:50-53`). Они участвуют в `gower.find_similar` и в `similar_examples=len(similar)` (`api/recommend.py:49-50`). `similar` всегда 5, даже если все 5 — отмененные прототипы. `_confidence:505-507` вычитает только за `0`.
2. **Gower веса `gower.py:58-70` экспертные.** `features:1.6`, `world_type:1.5`, `engine:0.6`. Движок почти не влияет — противоречит идее «похожие по технологиям». `RESOLUTION_TO_NUMBER:72-74` знает только `720p/1080p/1440p/2k/4k/2160p`. `768p/900p/1200p/1600p` из `enums.py:206-227` дают `None` и исключаются из сравнения (`gower.py:136-137`). Два масштаба разрешения в проекте: `hardware.RESOLUTION_FACTOR` (`1.0/1.6/3.0`) vs `gower` (`2.0/2.5/4.0`) — несогласованы.
3. **Канонизация движка `gower.py:22-55`:** все не-Track1 (`id tech, anvil, decima, fox, havok, RAGE, Fox Engine, Creation`) схлопываются в `custom`. Ваш PDF — это сплошь `id Tech 1, RenderWare, RAGE, Fox Engine, Creation 2, Dunia, CryEngine 1, EAGL`. Для них поиск похожих — мусор: `Doom` и `Starfield` оба `custom` и потому «похожи».
4. **Железо 51/79:** методика `raster_score=PassMark/38041`, `rt_score=technical.city/91.3` (`README:268-269`). Внешний якорь только 3 карты (`test_calibration.py:180-203`), допуск 25% (`1.7-2.7` при истине `2.1`). Дрейф на 20% пройдет. `single_thread` нигде не калибруется.
5. **Источники:** тест `test_every_published_record_has_source` проверяет наличие URL, не валидность. В вашем PDF источники `1. Quora про Q9650`, `6. YouTube`, `7. Reddit` — мусор для DSS. Если такие попадут в `seed`, тест их пропустит. `furor_influential.json` «проверен через Wikipedia API» (`README:368`) — Wikipedia не первичный источник по perf.

## 4. Рекомендации: TOPSIS + rules + риски

1. **Двойной учет confidence:** критерий `confidence` + `risk=(complexity-1)/4*0.6+(1-confidence)*0.4` (`recommender.py:412`). Один и тот же `confidence` тянет дважды.
2. **`resource_fit:201-212`:** `0.5+balance/8`. Диапазон почти всегда `0.4-0.6`. Не различает.
3. **`concept_fidelity=1+concept/2`, `quality=(quality+2)/4` (`recommender.py:415-416`)** — линейные перекодировки разных шкал (`-2..0` vs `-2..2` vs `1..5` vs `0..1`). Векторная нормализация TOPSIS чувствительна к масштабу до нормализации + к выбросам. Веса `WEIGHT_PROFILES:48-69` экспертные.
4. **`rules.py:20,103-112` LEGACY:** RT требует только `modern_platforms` непустым. Проект `pc_windows+ps4` с RT пройдет с `condition`, а железо подберет десктоп с RT, проигнорировав PS4. Оценка только PC, но анкета принимает 11 платформ. Для `ps5/xbox_series/switch/android` просто `-0.15 confidence` (`hardware.py:510-515`) и тот же PC-референс. Пользователь с PS5 получит «RTX 3060» — бессмысленно.
5. **P2P:** `README:497-500` говорит «топологии не различаем», а код уже различает (`schemas/catalog.py:78,84`, `hardware.py:253-256`: `p2p+0.04, lockstep+0.08`). Документация отстала. При этом налог хоста `Helldivers 2` (P2P хост тянет симуляцию) не моделируется: `p2p` дешевле `lockstep` всегда, что для шутеров неверно.
6. **Риски `recommender.py:129-322`:** 10 эвристик. Нет риска «P2P хост», «GC Stop-the-World» (кейс Minecraft из PDF), «D3D11on12 сериализация» (Witcher 3), «DX9 draw-call wall» (GTA IV), «Far Lands float» — все ключевые уроки PDF не закодированы как риски. Они есть только текстом в `pros/cons` отдельных методов, если есть.

## 5. PDF-реестр vs база знаний — разрыв

Ваш PDF требует от карточки: движок/рендер/сеть, релиз ПК, версии, причина репутации, `+/-` с подсистемой и ценой, влияние, DSS-теги, источники.

Что есть в `Method`:

- `pros/cons/limitations: str[]` без структуры: нет `affected_subsystem`, `expected_effect`, `source_per_bullet`, `confidence_bounds`. `docs/calibration-protocol.md:36-41` требует проверки «по отдельным утверждениям», код проверяет только заполненность (`test_every_seed_method_has_application_steps`, `test_every_published_method_has_a_parent_function`).
- `application_steps`, `used_in_projects` отдаются API (`api/catalog.py:88,105`), но в UI не показываются — `README:522-523` честно фиксирует как «точечный задел». Главное требование «выдай плюсы/минусы решений» в интерфейсе обрезано.
- Фактологические уроки PDF (`128 visplanes -> краш`, `DX9 10k draw calls -> CPU wall`, `D3D11on12 -> -40%`, `Far Lands 12550824 = 2^31/171.103`, `RDR PC 2024`, `Payday Diesel 3.0 x64+DX11`, `Remnant VSM`, `FC6 RT PC-only`) не закодированы как `rules`/`risks`/`requires_hw_features`. Это текстовые PDF вне `seed/`. Система их не знает.

## 6. Конкретные баги/несостыковки с линиями

- `frontend/src/screens` 12 файлов, `README:455` «на выбор: ПК и macOS» — backend знает 11 платформ (`enums.py:385-396`). Калибровка mobile/console через UI невозможна.
- `input_fingerprint: schemas/catalog.py:600-607` хеширует только `profile+basket`, не `algorithm_version/dataset_version`. Два одинаковых входа на разных версиях дадут одинаковый `input_key` при разном результате. Дефект воспроизводимости.
- `repositories.methods_by_codes:49-54` молча игнорирует неопубликованные коды. Корзина с черновиком тихо считается пустой, только риск `unknown_method` (`recommender.py:145-152`) спасает, но `hardware` уже посчитан без них.
- `aggregate_load:770-804` нормализация `-6..+6 -> 0..100`, нейтраль 50. Два конфликтующих метода дают 50 («не влияет»), хотя реально «неизвестно». Тест `test_conflicting_methods_do_not_stack_effects` фиксирует 50 как правильное.
- `admin.py:327-346` `_coerce`: `int("3.5")` -> `0`, `float("bad")` -> `0.0` молча. Импорт с мусором пройдет как нули, потом `record_problems` может не поймать.
- `seeder.seed_examples:223-247` пропуск строк без `source_url:233-234` молча. Битый `track1/*.json` ужмется без ошибки.
- `hardware.json:3298 строк` — CPU `single_thread 0.47-0.55` при `multi 0.10-0.15` для класса 1-2: ST почти одинаков, MT различается в 1.5x. Выбор только по MT при одинаковом ST даст случайный класс для ST-bound игр.
- CI `.github/workflows/ci.yml` (по README:422-427) гоняет тесты+миграции+typecheck+build, но не `smoke_check.py` (82 проверки) и не прогон `wild66`. Сквозная гарантия вне gate.

## 7. Пробелы (не баги, но бьют по 70% perf)

Чтобы дойти до «ошибка perf ~30%», а не «попадание в ворота 200%», не хватает в анкете/модели (часть уже видна как `modeling_gaps:180-227`, но этого мало):

`качество кода/движка`, `число источников света/теней`, `разрешение теней/VSM vs CSM`, `RT-уровень (GI/reflection/shadow)`, `плотность растительности/толпы`, `размер текстур/HD-pack`, `overdraw/fill-rate`, `shader complexity`, `IOPS vs sequential диска`, `streaming pool eviction`, `GC/ managed heap пики` (сейчас только `+1GB`), `unified bandwidth`, `DLSS режим Quality/Performance`, `FG latency/артефакты`, `сеть loss/latency/tickrate сервера`, `thermal/power limit ноутбуков`, `драйвер/ОС оверхед`.

Без них формула принципиально не может дать 30% — только класс.

## 8. Что чинить первым для вашей цели

1. **Определить метрику:** или «доля в ±1 класс ≥70%» (текущая, честно назвать «грубый класс»), или «медианная ошибка raster ±30%». Сейчас смешаны. Зафиксировать в `calibration-protocol.md` + тест на `wild66.json` автоматом, иначе все остальное — косметика.
2. **Автопрогон wild66/200 в CI** с матрицей `720p/low/30 ... 4k/ultra/60` из протокола `:31-34`. Исключения считать отдельно, не выкидывать молча.
3. **Разделить CPU ST/MT:** выбор CPU по `max(ST_need, MT_need)`, а не только MT. Иначе старые/однопоточные проекты всегда мимо.
4. **Убрать ручной `perf_class`:** вычислять из `raster/multi` + явные исключения отдельным полем, иначе дрейф.
5. **Импортировать уроки PDF в `rules/risks`:** `DX9+много draw calls -> риск`, `D3D11on12 -> риск`, `P2P+экшен -> риск хоста`, `managed+чанки -> GC-риск`, `float32+большой мир -> origin shifting обязательно`. Сейчас это знания в PDF, а не в системе.
6. **Донести `pros/cons/steps/used_in` до UI** + структурировать `pros/cons` по подсистемам. Иначе требование «выдай плюсы/минусы решений» не выполнено на экране, только в API.
7. **Починить `input_key`, платформы UI, `draw_call` потолок, `simulation_radius` насыщение, `coerce` молчаливые нули.**

Без п.1-4 любые правки весов `0.20/0.25` — это подгонка под 8 точек, запрещенная вашим же протоколом.

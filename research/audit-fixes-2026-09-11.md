## 0. Как проводился аудит и чем подтверждались выводы

> **Тесты не использовались как доказательство корректности.** Прогон
> `pytest` / `vitest` ниже приводится только как проверка на *регрессию*: он
> показывает, что исправление ничего не сломало, но ничего не доказывает о
> правильности модели. Каждое исправление обосновывается либо чтением кода,
> либо прямым запросом к БД, либо независимым инструментом.

Использованные способы проверки (в порядке значимости):

| Способ | Что даёт |
|---|---|
| Прямые SQL-запросы к production-БД | фактическое состояние данных, а не самоотчёт |
| `tools/check_seed_convergence.py` | сборка с нуля = +3 полных сида = +3 старта приложения (все 18 таблиц) |
| `tools/audit_evidence.py` | обязательные нули покрытия и объявленные пробелы |
| `tools/check_research_invariants.py` | движок воспроизводит числа из `research/category_verification.md` |
| `alembic check` | схема из миграций = модели SQLAlchemy |
| `pyflakes` | мёртвый код, неиспользуемые импорты, теневые имена |
| Чтение кода (несколько проходов: сервисы, сиды, API, схемы, модели, frontend, конфиги) | контракты, которые не видны в данных |
| `pytest` / `vitest` / `tsc` | **только** регрессия |

Классы искались целенаправленно: молчаливая потеря данных, собранные-но-неиспользованные
данные, миграции, не воспроизводящие модели, скрытая недетерминированность сидов,
устаревшие производные данные, подстановка неизвестного значения известным
значением по умолчанию, мёртвый код, заглушки, необоснованные решения.

## 2. Дефекты и исправления

### 2.1 Целостность доказательств

**Д-1. Явный `null` из пака записывался как строка `"None"` и отдавался через API.**
`backend/app/seed/pack_loader.py`, `_upsert_claim`.
`payload.get("value", "")` возвращает `None` при явном JSON `null` (значение
присутствует, поэтому значение по умолчанию `""` не срабатывает), а `str(None)`
даёт `"None"`. Строка попадала в `value_text` и отдавалась клиенту как значение
утверждения. В production-БД это затронуло **1760 строк**.
*Исправление:*
```python
raw_value = payload.get("value")
...
value_text=("" if raw_value is None else str(raw_value))[:4000],
value_num=raw_value if isinstance(raw_value, (int, float)) else None,
```
плюс выравнивающий проход в ветке существующей строки (лечит уже записанные базы):
```python
if (existing.value_text or "") == "None" and existing.value_num is None:
    existing.value_text = ""
    changed = True
```
*Обоснование:* отсутствие значения обязано остаться отсутствием. Строка `"None"`
— это выдуманное значение: она выглядит как измеренная величина и неотличима от
настоящего текста утверждения. Правильное состояние — пустое `value_text` при
`value_num = None`.

**Д-2. Два CPU с приблизительными значениями были помечены `measured`.**
`backend/app/seed/fixes_v2.py`, `_MEASURED_CPU_MULTI`.
Комментарии в коде прямо говорили «approx from common list (not in fetch;
derive)», но значение писалось с `evidence_basis = "measured"`.
*Исправление:* значения `Core i5-13600K` / `Core i5-14600K` вынесены в новый
словарь `_APPROX_CPU_MULTI`; добавлена ветка
`elif (approx_multi := _APPROX_CPU_MULTI.get(row.model)) is not None:`, которая
пишет `evidence_basis = "derived"` с явной нормализующей заметкой.
*Обоснование:* `measured` — это утверждение «величина измерена». Приблизительная
оценка из общего списка измерением не является. `derived` с заметкой честно
сообщает происхождение числа. Итог: CPU `measured 49 / derived 2`.

**Д-3. Дата проверки ссылки выдавалась за дату публикации.**
`backend/app/seed/sources.py` (`UE_DISTANCE_SHADOWS`), `evidence_catalog.py`
(`UE_CITY_SAMPLE_PCG`).
*Исправление:* обе даты приведены к `n/a` с пояснением.
*Обоснование:* у обновляемой документации Epic даты публикации не существует;
конкретное число вводило в заблуждение (выглядело как дата выхода страницы).

**Д-4. Проход правки подставных дат не покрывал конкретные даты.**
`backend/app/seed/corrections.py`, `correct_placeholder_source_dates`.
Функция заменяла только «заглушки» и «1 января», поэтому конкретная дата,
оказавшаяся датой проверки ссылки, выживала в уже собранной БД.
*Исправление:* добавлено условие «реестр прямо объявляет `n/a`»:
```python
placeholder = bool(_YEAR_ONLY_DATE.match(current)) or current in _PLACEHOLDER_DATES
undated_declared = expected == "n/a"
if not placeholder and not undated_declared:
    continue
row.published_date = expected
```
*Обоснование:* если реестр источников объявляет отсутствие даты, то любая
конкретная дата в базе недостоверна по определению. Иначе класс дефекта
возвращается при каждом повторном заполнении.

**Д-5. 28 источников имели **незадекларированную** пустую дату публикации.**
`backend/app/seed/reviewed_methods.py` (4 записи), `backend/app/seed/evidence_catalog.py`
(`EXTRA_SOURCES`, 24 записи).
Из 936 источников 105 объявляли отсутствие даты (`n/a`), а 28 оставляли поле
пустым. Собственный аудит проекта разделяет эти состояния явно: `n/a` →
`declared_undated_living_doc` (объявленное отсутствие), пусто →
`missing_published_date` (пропуск). То есть 28 записей читались как незакрытые
дыры — ровно тот класс, который запрещён правилом «отсутствие источника ≠
совместимость; пробелы объявляются, а не замалчиваются». Собственная строка
документации `sources.py` прямо это фиксирует.
*Исправление:* для каждой записи проведена **проверка страницы** и проставлено
честное значение:

| Запись | Значение | Как установлено |
|---|---|---|
| `RESEARCH_S42_RIOT_SCALABILITY` | `2020-12-15` | дата показана на странице статьи Riot Games |
| `RESEARCH_S35_PMI_PERT` | `2011` | PMI Practice Standard for Scheduling, 2-е изд. (ANSI PMI PSF-S-2011) |
| 20 записей офиц. документации (UE, Unity, CRYENGINE, Microsoft Learn) | `n/a` | страницы не содержат даты публикации (проверено выборочно по каждому вендору) |
| `RESEARCH_S43_HAMMER`, `S44/S45_HEROENGINE_*`, `S49/S50/S51_*`, `S57_NASA_GLOSSARY` | `n/a` | живые справочные страницы/графики без даты публикации |
| `KHRONOS_ASYNC_COMPUTE`, `MS_DIRECTSTORAGE_GUIDANCE`, `UNITY_GPU_BUDGETS`, `VALVE_REWIND` | `n/a` | живые документы/файлы в репозитории; у них есть история изменений, но не дата публикации |

*Обоснование:* пустое поле — это молчание; `n/a` — это утверждение. Для двух
записей дата реально существует, поэтому вместо `n/a` проставлено проверенное
значение: подставлять `n/a` источнику с известной датой было бы новой ложью.
Итог: `blank published_date` **28 → 0**, `declared n/a` **105 → 131**,
в отчёте аудита строка `missing_published_date` исчезла.

**Д-6. `source_date` у функций-заглушек оставался пустым при объявленном `n/a`.**
`backend/app/seed/corrections.py` — закрыто тем же правилом Д-4 (реестр `n/a`
перекрывает конкретное значение).

### 2.2 Схема БД и миграции

**Д-7. `Conflict.conflict_type` по умолчанию имел значение вне перечисления.**
`backend/app/models/entities.py`. Значение по умолчанию — `"conflict"`, которого
нет в `ConflictType`; строка с таким значением не проходит ни одну проверку
типа и не сопоставляется ни с одним типом конфликта.
*Исправление:* `default="unknown"`; в БД `conflict_type='conflict'` → **0 строк**.
*Обоснование:* значение по умолчанию обязано принадлежать собственному
перечислению, иначе это скрытое недопустимое состояние.

**Д-8. Свободный текст стадии терялся: `normalize_stage` возвращал код и заметку, а оба места вызова брали `[0]`.**
`backend/app/seed/pack_loader.py`. Docstring самой функции требует, чтобы
вызывающий сохранил текст, — но ни один вызывающий его не сохранял.
*Исправление:* добавлена колонка `WorkPackage.stage_note`, новая миграция
`backend/alembic/versions/20260911_wpstagenote01_work_package_stage_note.py`
(ревизия `wpstagenote01`, `down_revision="meta01_research_meta"`, защищённый DDL,
обратимый downgrade), нормализация выполняется в одном месте
(`_upsert_work_package`) и заметка сохраняется; есть выравнивающая ветка для
уже собранных баз. В БД `stage_note` непустых — **512**.
*Обоснование:* функция, возвращающая два значения, существует ровно потому, что
второе значимо. Его отбрасывание — потеря собранных данных.

### 2.3 Пайплайн сидирования

**Д-9. Путь «старт приложения» не канонизировал граф: `conflicts` писались, а рёбер не появлялось.**
`backend/app/seed/seeder.py`, `sync_function_taxonomy`.
`seed_all` вызывал `sync_dependency_graph` + `break_dependency_cycles` +
`dedupe_symmetric_relations` + `apply_relation_resolutions`, а путь старта
приложения — нет. Одна и та же БД в зависимости от входа получала разное
состояние графа.
*Исправление:* в `sync_function_taxonomy` выстроен тот же канонический порядок,
что и в `seed_all`.
*Обоснование:* два входа в одну базу обязаны сходиться к одному состоянию —
это и проверяет `check_seed_convergence.py`. Иначе «пусто в графе» зависит от
того, как запустили приложение.

**Д-10. Проверка знаний падала на «висячей» связи.**
`backend/app/seed/seeder.py`, `validate_knowledge_base` — `db.get(Method, link.method_id)`
мог вернуть `None` и обращение к `.code` падало, прерывая валидацию.
*Исправление:* пропуск отсутствующей цели:
```python
linked = {
    method.code
    for link in db.scalars(select(MethodEngineLink))
    if (method := db.get(Method, link.method_id)) is not None
}
```
*Обоснование:* валидатор, падающий на дефектных данных, не может их обнаружить —
он маскирует дефект падением вместо сообщения.

### 2.4 Расчётная модель

**Д-11. Split-screen умножал draw calls на **сетевых** игроков.**
`backend/app/services/hardware.py`, `_estimated_draw_calls`: было
`base *= max(2, profile.player_count)`. Разделённый экран — это локальные
представления сцены, а `player_count` — сетевые участники.
*Исправление:* `base *= _local_views(profile)`.
*Обоснование:* это подстановка чужого входа. Сетевой игрок не рендерится на
данной машине; его число не влияет на число проходов отрисовки.

**Д-12. `_gpu_feature_support` возвращал `False` для «нет в каталоге».**
`backend/app/services/hardware.py`. Отсутствие записи о функции трактовалось как
доказательство её отсутствия, из-за чего корректные GPU исключались из подбора.
*Исправление:*
```python
if req.startswith(("dlss", "fsr", "xess")):
    return True if any(f.startswith(req) for f in features) else None
```
*Обоснование:* «неизвестно» и «опровергнуто» — разные состояния. Сведение
первого ко второму — это подстановка неизвестного значения известным, то есть
выдуманное решение.

**Д-13. Недостижимая ветка в подборе GPU.**
`backend/app/services/hardware.py`: условие `reference_gpu is not None and
reference_gpu.vram_gb < vram_gb` не могло выполниться, потому что `_pick_gpu`
фильтрует пул по `vram_gb` заранее.
*Исправление:* ветка удалена, вместо неё поясняющий комментарий.
*Обоснование:* недостижимый код читается как действующая логика и вводит в
заблуждение при следующей правке.

**Д-14. Экономии и доплаты по подсистеме с нулевой базой исчезали молча.**
`backend/app/services/hardware.py`, `_apply_method_effects`. При `base <= 0`
ветка делала `continue` (экономия) или умножала на ноль (доплата), и решение
никак не отражалось в результате.
*Исправление:* оба случая объявляются в `exclusions` с пояснением, что модель не
начисляет базовую стоимость этой подсистемы.
*Обоснование:* неначисленное решение обязано быть видимым. Тихий `continue`
превращает «не применено» в «применено и дало ноль» — читатель не отличит.

**Д-15. Мёртвый код в планировщике и лишний запрос на каждую зависимость.**
`backend/app/services/planning.py`, `_methods_with_dependencies`: холостой цикл
`for edge in edges`, только присваивавший неиспользуемые локальные переменные и
обращавшийся к `nodes.get(edge.source_node_id)`; недостижимая ветка
`elif not target_code and target is None`; `known_methods` перезапрашивался
внутри цикла.
*Исправление:* мёртвый код удалён, `by_id` и `known_methods` подняты из цикла.
*Обоснование:* запрос методов на каждой добавленной зависимости — скрытая
квадратичная стоимость; мёртвые ветки искажают чтение.

**Д-16. Мёртвые сущности и необоснованные константы без объяснения.**
`backend/app/services/graph.py` — неиспользуемый счётчик `unsupported` и его
инкремент; `backend/app/services/rules.py` — неиспользуемая функция
`_level_value` и её импорт `Level3`. Константы-экспертные допущения (делитель
`/4.0`, веса тяжести, значение `0.4` для неизвестного) были без объяснения.
*Исправление:* мёртвый код удалён; допущения задокументированы в docstring.
*Обоснование:* число, придуманное без объяснения, невозможно ни проверить, ни
оспорить; после документирования оно становится проверяемым допущением.

### 2.5 API

**Д-17. Импорт JSON молча ничего не делал при неверном ключе верхнего уровня.**
`backend/app/api/admin.py`.
*Исправление:* HTTP 400 с описанием, какой ключ ожидался.
*Обоснование:* «успешный» импорт, не создавший ни одной записи, — худший вид
ошибки: пользователь считает данные загруженными.

**Д-18. Импорт мог создавать опубликованные записи.**
`backend/app/api/admin.py`: колонка `status` из файла проходила в новые строки.
*Исправление:* `status` всегда отбрасывается из импортируемых данных, новые
строки принудительно `DRAFT`.
*Обоснование:* публикация — это осознанное действие в интерфейсе, а не побочный
эффект загрузки файла.

**Д-19. Либеральное приведение булевых значений.**
`backend/app/api/admin.py`: `"no"`, `"false"` и любой мусор молча становились
`False`.
*Исправление:* пустая строка пропускается (не `False`), распознанные токены
отображаются в `True`/`False`, нераспознанные вызывают `ValueError`.
*Обоснование:* молчаливый `False` — это подстановка значения, которого в файле
не было. Ошибка ввода должна быть видимой.

**Д-20. Отчёт игнорировал запрошенные `team` и `include_dependencies`.**
`backend/app/api/recommend.py`, `_report_data` — расписание считалось
жёстко зашитыми `"small_2_5"` и `True` независимо от запроса.
*Исправление:* параметры `team` и `include_dependencies` добавлены в
`RecommendationRequest` и протянуты в `planning.schedule`.
*Обоснование:* результат обязан зависеть от запроса; иначе интерфейс показывает
выбор пользователя, а расчёт его не учитывает.

### 2.6 Frontend

**Д-21. Профиль не согласовывался: снятие split-screen оставляло `local_view_count`, отключение frame generation — `base_render_fps`.**
`frontend/src/store.tsx`. Сохранённое `base_render_fps > target_fps` приводило к
HTTP 422 при следующем запросе.
*Исправление:* `reconcileProfile(prev, patch)`, вызываемый из `updateProfile`:
снимает `local_view_count` при удалении функции разделённого экрана, снимает
`base_render_fps` при выключенной генерации кадров или при
`base_render_fps > target_fps`.
*Обоснование:* параметр, потерявший смысл, обязан исчезнуть из запроса, а не
передаваться дальше и вызывать отказ сервера.

**Д-22. Восстановленный профиль мог принести устаревший псевдоним разрешения.**
`frontend/src/store.tsx`, `loadPersisted`: `target_resolution === '4k'`
нормализуется в `'2160p'`.
*Обоснование:* сервер принимает одно написание; сохранённое значение прежней
версии интерфейса иначе давало бы отказ.

**Д-23. Мёртвое поле `resultStale`.** `store.tsx`, `App.tsx`,
`__tests__/store.test.tsx` — поле всегда было `false`, а зависящий от него
Callout «Данные изменены» был недостижим.
*Исправление:* поле и блок удалены, четыре утверждения в тесте убраны.
*Обоснование:* недостижимый интерфейс создаёт ложное впечатление, что
устаревание результата отслеживается.

**Д-24. Ошибка `/catalog/stage-guidance` оставляла вечное «загружается…».**

### 2.8 Верификация источников (найдено при перегенерации отчёта)

**Д-30. Отчёт верификации был затёрт прогоном «только паки, без сети».**
`research/verification_report.json`: было 271 634 байта с ключами

*Исправление:* полный прогон `tools/verify_sources.py` (сеть доступна) —

Затёртая версия сохранена в `tmp/verification_report.packs-only.bak.*`.
*Обоснование:* отчёт — расходуемый, но не безразличный артефакт; прогон,
сужающий охват, не должен молча заменять полный отчёт.

**Д-31. `claim_dangling_source` давал 3 ложных срабатывания.**
`tools/verify_sources.py`, проверка `dangling`. В модуле есть функция
`_self_justified()`, чей docstring прямо описывает этот случай
(«`derived`-утверждение с формулой и входами вообще не ссылается наружу, и его
отсутствие в `source_id` не дефект… без неё эта проверка давала 3 ложных
срабатывания, пока аудит показывал 0»). Она применена к `numeric_claim_without_source`,
но **забыта** в `dangling`, поэтому `verify_sources.py` показывал 3, а
`audit_evidence.py` — 0. Расхождение двух инструментов делает отчёт недостоверным.
*Исправление:* добавлено `and not _self_justified(c)`.
*Обоснование:* инструмент противоречил сам себе; починка восстанавливает
согласие с `audit_evidence.py` и валидатором базы. Затронуты
`research:frame_budget_60`, `research:resolution_ratio_4k`,
`research:memory_headroom` — у всех есть `formula` и `input_parameters`.

**Д-32. Объявленный маркер отсутствия ссылки считался мёртвым адресом.**
`tools/verify_sources.py`, `http_check`. Значение `user_defined:catalog_dependency`
— это **декларация**, которую `declare_evidence_gaps` ставит 30 конфликтам,
выведенным из структуры каталога. Проверка пыталась «сходить» по ней как по URL
и помечала `dead` («not an http(s) url»), из-за чего `url_dead` показывал 34
вместо 4. Хуже: `tools/repair_dead_links.py` читает этот отчёт и попытался бы
«починить» саму декларацию.
*Исправление:* введён отдельный статус `declared`; маркеры попадают в новую
информационную графу `url_declared` (30) и не смешиваются с дефектами; в
markdown-сводку добавлена строка «объявленное отсутствие ссылки, не адрес».
*Обоснование:* то же правило, что и для дат: объявленное отсутствие — решение,
а не пропуск. Смешение их завышало счётчик дефектов в 8 раз.

**Д-33. Три адреса источников действительно мертвы.**
Из 759 уникальных URL базы недоступны 3 (остальные 50 «ошибок» — туннель прокси
502, то есть сетевой шум, а не мёртвые ссылки).
*Исправление:* два случая — переезд адреса у того же вендора, заменены на
проверенные 2xx (`docs.unity3d.com` перенесла справочник 6000.x под
`/Documentation/Manual/`): `UNITY_SHADERLOAD` и `RESEARCH_S31_UNITY_JOB_OVERVIEW`.
Третий (`DF_ITTakesTWO`) замены не имеет — см. §4.2, решение не принято.
*Обоснование:* замена только на пробитый 2xx того же вендора и той же темы;
URL не выдумывается, а источник без проверенной замены не подменяется похожим.

**Д-34. Исправление адреса в реестре не доезжало до существующей базы.**
`evidence_catalog.sync_sources` намеренно не перезаписывает непустые поля
(правка администратора важнее), поэтому смена URL в реестре лечит только базу с
нуля: 404 продолжали жить в `evidence_sources`, `methods`, `conflicts`,
`method_engine_links` и `hardware_*`. Тот же класс, что был у дат публикации.
*Исправление:* добавлена идемпотентная функция
`repair_dead_source_urls(db)` в `backend/app/seed/corrections.py` со словарём
`SOURCE_URL_REPLACEMENTS`; вызывается из `declare_evidence_gaps`, поэтому
срабатывает и на старте приложения, и при полном сиде.
*Обоснование:* правка реестра без прохода по записанным строкам — это
исправление, которое не исправляет. Срабатывает только на точное совпадение
прежнего адреса, поэтому собственная ссылка администратора не заменяется.

**4.2. Источник `DF_ITTakesTWO` остаётся недоступным — решение не принято.**

Это меняет доказательный статус 3 утверждений, поэтому решение оставлено за

## 5. `tmp/proposal_vram_quantization.md` — квантование запаса VRAM

**Главное подтверждено: прошлый аудит ошибался.**
- `hardware._required_index` в `backend/` **не существует** (0 совпадений). В
  `tmp/audit_gpu_pick.py:66` стоит `hasattr`-защита ⇒ `idx = None`; на строке **67**

  То есть фиктивное требование 0.5 навязано всем сценариям — и в растр, **и в RT**
  (документ упоминает только растр). Функция при этом не «вызывается» — выражение не
  вычисляется; на вывод это не влияет, но формулировку надо поправить.
- Числа аудита воспроизведены ровно: медиана **31 %**, максимум **104 %** (F.E.A.R.,
  3.92 → 8 ГБ), доля > 50 % = **17 %**.
- Пересчёт по реальному конвейеру воспроизводится: base **+25.0 / +73.9 / 8 %**,
  min **+33.3 / +86.0 / 32 %**, max **+17.7 / +114.3 / 12.5 %** (в документе «13 %» —
  округление вверх). Оговорка: `tmp/quality_sweep.json` **не содержит** VRAM выбранной
  карты — нужен join к `hardware_gpu`; в документе это не сказано.
- Сетка VRAM подтверждена: `{0, 2, 4, 6, 8, 10, 11, 12, 16, 20, 24, 32}` — 12 значений.
- Кейсы подтверждены: F.E.A.R. need 3.9 → GTX 1050 Ti (4 ГБ), **+2.6 %**; CS 2 need 4.6
  → RTX 3060 Ti (8 ГБ), **+73.9 %** (порог 0.5053, максимум raster среди 6-ГБ карт 0.37 —
  не проходит ни одна).
- Вариант Г действительно требует **нового поля схемы**: `HardwareEstimateOut`
  (`catalog.py:728-744`) отдаёт `estimated_vram_gb`, `required_gpu_index`, `reference_gpu`,

  попасть не может. Документ это признаёт — противоречия нет.

**Новая ошибка документа (§6).** Утверждение, что в аудите F.E.A.R. получила «RX 580 —
слабейшую карту, прошедшую перф-порог», **неверно**: реальный выбор — **RTX 5060** (8 ГБ,

## 6. Пределы профиля не ограничивают — проверка пункта без предложения

Пункт из `parameter-audit-2026-09-12.md` («пределы не ограничивают») остался единственным
без документа-предложения. Инвентарь составлен заново.

| Поле | Читается в `hardware.py`? | Что делает | Где |
|---|---|---|---|
| `ram_limit_gb` | да | **не клампит**; нормализация `_memory_pressure` + строка в `unmet_limits` | `2445`, `2628-2632` |
| `vram_limit_gb` | да | **не клампит**; то же | `2444`, `2623-2627` |
| `size_limit_gb` | косвенно | жёстко исключает методы (< 2 ГБ, `impact_disk >= 2`) | `rules.py:161`, `100`; `hardware.py:2309-2313` |
| `complexity_tolerance` | нет (в rules) | жёстко исключает методы по сложности | `rules.py:155-158` |
| `*_budget` (cpu/gpu/ram/vram) | нет (в rules) | **не инертны**: критерий `resource_fit` (TOPSIS) | `rules.py:96-99, 312-325`; `recommender.py:512` |
| `streaming_pool_gb` | да | **меняет** состав RAM/VRAM | `hardware.py:1683-1689`, `1640-1664` |
| `draw_call_budget` | да | только предупреждение | `hardware.py:2642-2646`, оценщик `933-950` |
| `deadline_weeks` | нет | только risk-карточка | `recommender.py:317-338` |

**Воспроизведение.** При `2160p / ultra / scale=very_large` RAM = **16.9 ГБ** и не
зависит от `ram_limit_gb` (4 / 8 / 16 / 32 / 64 / None — одинаково); выводится строка
«Требуется 16.9 ГБ оперативной памяти при заданном пределе 8.0 ГБ»
(`hardware.py:2628-2632`). Точные 14.52 ГБ из аудита воспроизвести **не удалось** —
профиль аудита нигде не зафиксирован; ближайшие варианты дали 14.8 и 15.4.
Свип `draw_call_budget` 500 / 5000 / 50000: `ram, vram, cpu_seq, cpu_par, gpu_raster,
gpu_rt, budget, content, world_content` идентичны; меняется только текст предупреждения.
Понижения рекомендации из-за предела **не происходит** ни в одном случае.

**Вердикт по классу.**
- `draw_call_budget` — **объявленная граница**: docstring `hardware.py:933-938` прямо
  говорит, что значение нужно для выявления противоречия с лимитом, а не для выдачи FPS.
- `ram_limit_gb` / `vram_limit_gb` — **дефект контракта**, а не объявленная граница.
  Комментария, снимающего обязательность, нет; наоборот, блок назван «Обязательные
  ограничения» (`catalog.py:125`), а `unmet_limits` — «Явный список невыполненных
  обязательных ограничений» (`catalog.py:746-749`). При этом из того же блока
  `size_limit_gb` и `complexity_tolerance` действительно исключают методы.
- **Пределы не полностью инертны:** они меняют знаменатель `_memory_pressure`
  (`2378-2380`) и способны переключить bottleneck (при 1080p/60 `ram_limit=4 → memory`,
  `ram_limit=16 → cpu_main_thread`). Это диагностический эффект, а не ограничивающий.

**Поправка к аудиту:** утверждение «`*_budget` не влияют даже косвенно» **ошибочно** —
они входят в критерий `resource_fit` TOPSIS и меняют ранжирование методов.

## 9. Сквозные причины

1. **Постоянный базис памяти 6.60…7.25 ГБ** — общий корень и для провала `project_scale`,
   и для знаковой ошибки модели (+18 % на исправленном эталоне). Пока пол не убран,
   любая новая ось лечит симптом. Ни одно из пяти предложений базиса не касается.
2. **Три разных способа объявить пробел, и все три выглядят по-разному:**
   `note` (видно пользователю), пустой `{}` без `note` (неотличимо от «забыли»),
   `not_modeled` (выглядит как «цель учтена»). Единого реестра пробелов нет — это
   причина пунктов 4 и 14.
3. **Схема вывода не отдаёт данные для честного объяснения запаса** (нет избытка,
   нет источника, нет граничной карты) — отсюда требование нового поля в пункте 8.
4. **Категоричность формулировок.** «Никогда не выбирается», «единственная точка»,
   «нет ключа» — три из трёх не подтвердились буквально. При интеграции читать
   предложения с оговорками, а не как ТЗ.

## Приложение А. Что осталось непроверенным

Внешние источники: формула shared-памяти WDDM (`MIN(0.8·RAM, MAX(RAM−16, 0.5·RAM))`),
документы Intel 000020962 / 000041253 / 000094617, AMD PA-280, ядро Linux (amdgpu),
требования игр (F.E.A.R., CS 2), документация Unity/Epic, числа пропускной способности
(51.2 / 68.3 / 89.6 ГБ/с). Сеть не использовалась. Всё, что опирается только на эти
источники, требует отдельной проверки перед интеграцией.

Не воспроизведено: точные 14.52 ГБ из аудита параметров (профиль не зафиксирован).

## Часть 1. Углубление причин известных дефектов

### 1.1. Причина 50/50 подтверждена — но исправление уже написано и не подключено

В `defect-diagnosis` E1 значился как «не реализовано». Фактически **функция
замыкания обязательных зависимостей уже написана**, лежит в
`backend/app/services/rules.py:213` (`mandatory_dependency_closure`), содержит
правильную логику (транзитивный обход до неподвижной точки, отдельный список
пояснений) — и **не вызывается ни из одного места**:

```
$ grep -rn "mandatory_dependency_closure" backend/
backend/app/services/rules.py:213:def mandatory_dependency_closure(
```

Прогон на прод-БД (S16 Horizon Zero Dawn, корзина 6 методов):

```
applicable=True у всех 6,  scope=client у всех 6
accounted = 0/6     load cpu=50.0 gpu=50.0 ram=50.0 vram=50.0
```

То есть **дефект жив, а его лечение — мёртвый код**. Это не «план E1», это
незавершённая интеграция. Симуляция замыкания на 25 сценариях:

| | сейчас | с замыканием |
| --- | --- | --- |
| методов в расчёте | **60 / 114** | **141** (включая достроенные; часть выбранных всё ещё отсеивается) |
| S16 Horizon Zero Dawn | 0 / 6 | **8 / 6** |
| S19 Uncharted 4 | 0 / 5 | **3 / 5** |
| S05 Split Fiction | 1 / 4 | **9 / 4** |

**Уточнение к причине.** Потеря не «53 %», а **47 %** (54 из 114). Замыкание
чинит не всё: у S19 остаётся 3 из 5, потому что часть достроенных зависимостей
сама неприменима к профилю — это ожидаемое поведение каскада, но теперь с
названной причиной.

### 1.2. Причина C5 (дубликаты кейсов) — механизм подтверждён, но он хуже, чем описан

Схема кода `CASE_{game}_{i}`, где `i` — индекс примера **внутри метода**
(`pack_loader.py:635` и `:778`). Следствие, которое в предыдущем отчёте не
названо: **дедупликация происходит случайно**. Если игра встречается в двух
методах под одним индексом (например `_0`), записи **сливаются** в один кейс;
если под разными (`_0` и `_1`) — создаётся дубликат. Отсюда:

* 155 записей при **122** уникальных ключах `(название, год, движок)`;
* 27 групп дублей, 33 лишних записи (не «155 → ~107»: цель нормализации — **122**).

Это подтверждает план E2, но меняет ожидаемое число: 155 → **122**, а не 107.

### 1.3. Причина C6 (кейсы без функции) — не главная. Главная — кейсы не опубликованы

C6 описывал 84 function-only строки как недостижимые, потому что
`cases_for_methods` (`evidence.py:70`) матчит только по `method_code`. Это
**верно, но это второстепенная причина**. Настоящая причина пустой «Сверки с
практикой» — в другом (см. N1): функция обходит только **опубликованные** кейсы
(`repositories.game_cases`), а опубликовано **8 из 155**.

Проверка: если игнорировать статус кейса, число сценариев с пустой сверкой
падает с **12/25 до 0/25**. То есть C6 — про остаточные 84 строки, а N1 — про
все 147 невидимых кейсов.

### 1.4. Причина C9 (противоречивые рёбра) — пар не одна, а три

`defect-diagnosis` называл одну пару (`motion_matching` ↔
`animation_lod_budget`). Фактически таких пар **три**:

| Пара | Типы связей |
| --- | --- |
| `motion_matching` / `animation_lod_budget` | `dependency` + `hard_conflict` + `risk` |
| `full_path_tracing_pipeline` / `selective_ray_traced_effects` | `dependency` + `alternative` |
| `hardware_raytraced_gi` / `sdf_global_illumination` | `dependency` + `alternative` |

Вторая и третья **не были найдены**: `alternative` говорит «выберите одно»,
`dependency` — «держите оба». Это ровно тот же класс дефекта наполнения, что и
C9, и план E5 обязан закрыть все три пары, а не одну.

## Часть 2. Дефекты, которые были пропущены

### N1. Игровые кейсы не публикуются — 147 из 155 невидимы (высокая)

`pack_loader._upsert_case` (`pack_loader.py:297`) создаёт `GameCase` **без поля
`status`**, а модель по умолчанию даёт `draft` (`entities.py:474`). Публичный
слой (`repositories.game_cases`) фильтрует `status='published'`, поэтому в API и
в отчёте видны только 8 курируемых кейсов:

```
game_cases: total=155  published=8  draft=147
case_evidence с родителем-черновиком: 363 из 375
```

Последствия:

* «Сверка с практикой» пуста в **12 из 25** сценариев;
* 363 из 375 фактов-доказательств ссылаются на невидимого родителя — то есть
  доказательство опубликовано, а кейс, который оно подтверждает, — нет;
* `validate_knowledge_base` это **не ловит**: проверка `item.case_id not in
  case_ids` берёт `case_ids` по **всем** кейсам, без фильтра статуса
  (`seeder.py:557-560`).

Это тот же класс, что уже чинившиеся дефекты №4 (все claims были `draft`) и №5
(все sources были `draft`), но для третьей сущности — и он остался.

**Проверка эффекта исправления:** публикация кейсов убирает пустую сверку во
всех 25 сценариях (12/25 → 0/25).

### N2. Пакеты работ: две конкурирующие семьи, и используется не исследованная (высокая)

В таблице `work_packages` живут **две независимые семьи**:

| Семья | Код | Кол-во | Статус | Источник чисел |
| --- | --- | --- | --- | --- |
| формульная | `{method}.{kind}` | 802 | **published** | формула из `implementation_cost` / `complexity` (`evidence_catalog.py:1018`) |
| пакетная | `WP_{method}_{kind}` | 992 | **draft** | `effort_person_days` из исследовательских паков (`pack_loader.py:702`) |

Планировщик читает только опубликованные (`repositories.work_packages`), то есть
**всегда использует формульную семью**, а пакетная — 55 % таблицы — недостижима.

Пакетная семья содержит **исследованную, разобранную по строкам** оценку. Пример
(`research/packs/pack_world_streaming.json`):

```
async_loading_pipeline: p50=35, p80=60, basis=expert_estimate,
formula = "8d request/soft-reference discipline + 8d priority queue... + 7d IO
profiling + 6d install/transcode + 6d worst-case path testing"
```

В плане пользователя у этого же метода стоит **7.78** человеко-дня — формульная
оценка. Сравнение по всем методам:

```
методов: 124   одинаковый P50-итог: 0   различается: 124
сумма P50 по пакетной семье:  2430.00 чел-дней
сумма P50 по формульной:      1081.82 чел-дней
```

То есть **видимый план показывает ~45 % от исследованной трудоёмкости**, и
расходятся все 124 метода без исключения. Это не «дубликат данных»: это
потеря исследованного результата на уровне видимости. Отдельно это делает
счётчик `work_packages: 1794` в отчётах вводящим в заблуждение — реально
работает 802.

> Важно для плана: **нельзя просто опубликовать пакетную семью** — тогда на
> каждый метод будет 15 пакетов вместо 7 и трудоёмкость удвоится. Сначала
> нужно решить, какая семья авторитетна (обоснованно — пакетная, у неё есть
> формула и `basis`), и убрать/понизить вторую. Это меняет числа календаря и
> требует перегенерации `research/*.md` и сверки инварианта §2.10.

### N3. Мёртвый код: четыре функции, включая два несостоявшихся исправления

| Функция | Файл:строка | Что это |
| --- | --- | --- |
| `mandatory_dependency_closure` | `services/rules.py:213` | лечение E1 (см. 1.1) |
| `_load_indices` | `services/hardware.py:2064` | адаптер индексов, 45 строк, дубль логики |
| `_gain_text` | `services/recommender.py:916` | не вызывается |
| `_function_name` | `services/recommender.py:104` | не вызывается |

`pyflakes` их не видит (это функции уровня модуля, а не импорты), а обычные тесты
тоже — поэтому две «готовые правки» тихо не работают. Это класс дефекта:
**написанное исправление без вызова неотличимо от неисправленного дефекта.**

### N4. Расписание и нагрузка считаются по РАЗНЫМ наборам методов (высокая)

В одном и том же ответе `recommendations` планировщик уже делает замыкание
обязательных зависимостей (`planning._methods_with_dependencies`), а оценка
нагрузки и железа — нет. Результат противоречит сам себе:

| Сценарий | методов в корзине | учтено в нагрузке | методов в расписании |
| --- | --- | --- | --- |
| S16 Horizon Zero Dawn | 6 | **0** | **15** |
| S05 Split Fiction | 4 | **1** | **13** |
| S06 City Sample | 7 | 3 | 15 |

Пользователь одновременно видит «ни одно решение не влияет на ПК» (50/50) и
расписание на 15 методов. Это не два независимых дефекта, а **одна причина**:
замыкание применяется в одном месте и не применяется в другом. Правка E1 должна
делать расширение **один раз** и передавать один и тот же набор в
`assess_selected_methods`, `aggregate_load`, `estimate_hardware`,
`cases_for_methods` и `planning.schedule`.

### N5. `case_evidence.match_level` — 75 из 375 строк содержат прозу вместо кода (средняя)

`pack_loader` пишет `match_level=ex.get("relevance", "partial")`, а поле
`relevance` в паках — свободный текст. Контролируемый словарь
(`exact/partial/strong/direct/weak/contextual/analogous/none_found`) перемешан с
английскими абзацами:

```
CE_CASE_Minecraft_0_async_incremental_saves_0:
  "A shipped example of incremental, region-granular persistence: the sav..."
```

75 строк (20 %) не являются кодом. Поле нельзя ни сравнить, ни отфильтровать.
Тот же класс, что уже чинился для `work_packages.recommended_stage`
(`normalize_stage`), но для `match_level` нормализации нет.

### N6. Три противоречивые пары связей вместо одной

См. таблицу в 1.4. Дополнительно: по этим парам в базе **и** `hard_conflict`, **и**
`dependency`, поэтому движок честно применяет оба правила. Для пары
`motion_matching` / `animation_lod_budget` это приводит к исключению обоих
решений из расчёта (побеждает `hard_conflict`), хотя данные тут же требуют
«сохранять оба». Каждая пара даёт по два-три ребра в `dependency_edges`
(проверено запросом), поэтому вклад этих пар виден и в снимке рёбер.

**Закрыто 2026-09-11.** Сняты все три пары и четвёртая связь того же класса
(`risk` при `hard_conflict` той же пары: одно решение требует оставить оба
метода, другое — оставить один). Правка внесена в пакеты **и** в
существующую базу: сид не перетирает существующие строки, поэтому правка
каталога сама по себе в неё не попадает — для этого добавлен проход
`correct_contradictory_relations`, снимающий и строку, и ребро. Страж —
`tests/test_method_dependencies.py`: обязательная зависимость не может вести к
методу, с которым объявлена несовместимость, и у пары с `hard_conflict` не
может быть второго, мягкого типа.

### N7. `game_cases.world_type` / `network_mode` пусты у 134 из 155 (низкая)

В секции методов `pack_loader` жёстко пишет `world_type=""`, `network_mode=""`
(`pack_loader.py:642-643`); значения переносятся только в generic-секциях. У всех
8 опубликованных (курируемых) кейсов поля заполнены, у 147 пакетных — нет. После
исправления N1 это станет видно в API, поэтому чинить N1 и N7 нужно вместе.

### N8. Аппаратный слой: несоответствие причины и сообщения, мёртвая ветка, расхождение узкого места

* **Причина не совпадает с `unmet_limits`** (`hardware.py:2642-2662`). Если
  карты отсеял **API/апскейлер** (`api_compatible` пуст), а `required_hw`
  непуст, `unconfirmed` вычисляется по пустому `api_compatible` и сообщает «нет
  GPU с подтверждённой поддержкой обязательных возможностей: Compute Shaders»,
  хотя настоящая причина — API. Это остаток того же дефекта C2, что уже
  исправлялся, но в другой ветке.
* **Недостижимая ветка** `hardware.py:2688`: `_pick_gpu` при `required_rt`
  сначала фильтрует пул по RT и отдаёт `rt_missing=True` только когда RT-карт
  нет, поэтому условие `required_rt and not any(_supports_ray_tracing(g) ...)`
  ложно всегда. Сообщение не выводится никогда.
* **Узкое место противоречит индексу** (`hardware.py:2394-2408` против
  `:2085`/`:1035`): индекс GPU и стоимость кадра **суммируют** raster и RT, а
  `_bottleneck` сравнивает их **порознь**. При raster=RT=0.4 и CPU=0.5 узким
  местом назовётся CPU, хотя суммарный GPU (0.8) — ограничитель. Диагноз и
  подбор железа расходятся.

### N9. Сам аудит не проверяет публикацию — системная слепота (высокая, метадефект)

`tools/audit_evidence.py` читает `select * from game_cases` и `select * from
work_packages` **без фильтра статуса** (`:369`, `:496`). Поэтому официальный
аудит рапортует:

```
game_cases    -> total 155, pct_fully_ok 100.0, without_any_case_evidence 0
work_packages -> total 1794, missing_source_or_basis 0, p80_lt_p50 0
```

— то есть «всё полно», тогда как публично доступно 8 кейсов и 802 пакета. Аудит
измеряет **полноту содержания**, но не **видимость**. Именно поэтому N1 и N2
прожили незамеченными через все прошлые аудиты (включая сессии 8–12). Это не
частный баг, а пробел в методике проверки: любой новый набор сущностей, который
`pack_loader` создаст без явного статуса, снова станет невидимым и снова
пройдёт аудит «зелёным».

### N10. `apply_hardware_raw_values` перезаписывает провенанс безусловно (средняя)

`fixes_v2.py:393-394, 407-408, 421-422, 437-438, 449-450` присваивают
`row.evidence_basis` и `row.evidence_source_id` **без проверки «поле пустое»**, а
`updated += 1` выполняется для каждой строки. Функция вызывается и в
`seed_all`, и в `declare_evidence_gaps`, то есть на каждом сиде и старте.
Следствия: (а) правка администратора в этих полях не выживает; (б) счётчик
«обновлено» всегда 130 (51 CPU + 79 GPU) — идемпотентность только выглядит
идемпотентностью. Это нарушает собственное правило проекта «заполняется только
пустое», которое соблюдено в `relation_resolutions`.

### N11. Латентная недетерминированность выбора «жертвы» цикла (низкая)

`dependency_graph.break_dependency_cycles:437` берёт `select(Conflict)` без
`ORDER BY`, `_find_cycle` возвращает первый найденный цикл в порядке
`adjacency`, а `victim = max(candidates, key=...)` выбирает по коду. На
одинаковой базе результат детерминирован (порядок вставки стабилен, сверка
сходимости проходит), но при другом порядке строк в БД понизится **другое**
ребро. Выбор игнорирует `severity` и курируемость: может понизить настоящую
обязательную зависимость, оставив выведенную. Требуется `ORDER BY` и
приоритет «понижать выведенное, не курируемое».

### N12. Прочее (низкая, зафиксировать, не срочно)

* `correct_shadow_relation` (`corrections.py:101`) использует `next(...)` без
  `default` → `StopIteration`, если пары нет в каталоге. Сейчас недостижимо
  (пара есть, строка уже `complement`), но при правке данных станет падением
  всего сида, а не объявленным сбоем.
* `correct_placeholder_source_dates` (`corrections.py:400-403`) при объявленном
  в реестре `n/a` перезаписывает **любую** дату, включая заданную
  администратором; докстринг обещает обратное.
* `_SYMMETRIC_CONFLICT_TYPES` / `_SYMMETRIC_RELATIONS` не включают `overlap`.
  Это **осознанно** (в `pack_loader.py:378` прямо сказано, что `overlap`
  направленный), поэтому дефектом не считается — фиксируется как решение.
